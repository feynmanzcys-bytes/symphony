# Changelog

What changed in each release of symphony. The program (the bridge) and the mod share one version number. A release's notes start with its section here: the release workflow stops before building when the section is missing. Releases before v1.0.0 came out before the repository was public; their notes are kept below.

## v1.0.0 (2026-11-01)

The first public release. Update both parts: the program, and the mod with `claude plugin update symphony-bridge@symphony`.

- **The office needs a key**: the bridge makes a page key on its first start (`key` in the data folder, readable only by you) and keeps it across restarts. Every page and every call the pages make must show it (the mod still uses the account's token). `symphony` opens the office already signed in: the browser opens `open.html`, a file only you can read that passes the key on, so the key never appears on a command line. The bridge's log prints the office's address with `?key=`. A browser without the key gets a page that says how to get in. `symphony attach` and the demo read the key from the data folder (`-data`).
- **This machine only**: `-addr` must be `127.0.0.1`, `localhost` (which now means `127.0.0.1`) or `::1`, with a port from 1 to 65535; any other address stops the bridge. Connections from other machines are refused. When something else answers at the address (another program, a bridge with another data folder, or an older symphony bridge), symphony says so and stops instead of opening it: it shows the page key only to a bridge that proves it has the key, and so do `symphony attach` and the demo. `-autostart on` turns nothing on when the address is taken.
- Every answer carries security headers: a Content Security Policy that lets the pages load only the bridge's own files (no inline scripts, nothing from other sites), and other sites may not frame the pages. `/approve`'s script moved to `approve.js`.
- **The mod checks the bridge before it sends its token**: it sends a hash of the token and a random value to `POST /api/hello`, and only a bridge that knows the token can answer correctly. It checks again after a lost connection, and before each report while the bridge turns the session away as busy. A new message says when what answers isn't a symphony bridge the session can trust, or is older than the mod. `SYMPHONY_BRIDGE` must be on this machine (http) or use https; anything else gets a message and the bridge is never contacted.
- The mod no longer reads `.claude.json`: the login comes only from Claude Code's `$.session.identity()`, which answers only a mod installed through the organization's managed settings, so for most people the login chip stays empty. It no longer reports the git remote, and the bridge removes user names and passwords from a remote that an older mod sends.
- A malformed answer from the page (a decision other than allow or deny, say) leaves the decision to the terminal.
- Fixed: a chat item could reach the page with text it got later, so the next streamed piece showed twice (a data race). Each push now carries the state of the moment it was made.
- Fixed: at a task's end, the files git ignores in a member's worktree (build output, `.env`, `node_modules` ...) were deleted with the worktree. They are now moved to `.symphony/kept/<member>-<task id>/` in the member's folder (the task's `kept`).
- Fixed: at a task's end, a repository checked out in a member's worktree (a submodule it initialized, or one it made) lost the commits only it had, as the worktree was removed anyway. Now the worktree stays and the task fails, naming that repository.
- The terminal command the bridge gives for a session (`symphony attach <id>`) names `-addr` and `-data` when the bridge doesn't use the defaults.
- Fixed: a plain folder made a repository for a task committed everything in it, secrets included. `.env`, `.env.*`, key files (`*.pem`, `*.key`, `id_rsa*` ...), `.npmrc`, `.netrc`, `.pypirc`, `node_modules/` and `.DS_Store` now go in its exclude list before the first commit: they stay in the folder, out of the repository and the worktrees.
- **New defaults**: a new employee, an advisor and a task start with Claude Code's own settings ("Default") for the model, the thinking effort and the permission mode, instead of Opus, max and `bypassPermissions`; a returning employee keeps its last choices. Picking `bypassPermissions` shows a red line that says what it allows.
- **The pixel office's people are new**: hair, a face, a shirt in one of several colors, trousers and shoes, picked by seat; off duty they are gray. Size still follows the model, muscles the effort, and max effort still wears a red headband. symphony's own mark, two beamed eighth notes, is the logo in the bar, the sign on the back wall and the show on the lounge TV.
- The Messenger theme is now called **Coworkers** (its address stays `/t/messenger/`).
- Docs and community files: the README's install runbook verifies the download's checksum and asks before changes that outlast the install; new sections on cost and permissions and on what the bridge protects; `SECURITY.md` (how to report a vulnerability privately), `CONTRIBUTING.md`; CI runs on pull requests; Dependabot keeps the actions and Go modules up to date. symphony is an independent project, not affiliated with Anthropic; the manifests say so.

## v0.12.0 (2026-11-01)

- **Mission Control, the fourth theme**: a control room's wall for a second screen (`/t/mission/`, or the theme picker). The bar: the mission time since the bridge started, the desk sessions online over the headcount, the alarms (red while asks wait; a click opens the first), today's cost, the search box, a sound switch (a tone on a new alarm, off by default). The wall: one tile per session online — desk sessions and task members alike, a task's members with its colored stripe — and a dim one per account off duty, as many columns and rows as fit the window; each tile the name, the state in a word with its color, the model and effort, gauges for the context window's fill and the rate-limit windows, a sparkline of the tokens over the last minute, and what runs now; a waiting session's tile flashes. A tile opens the window (a member's beside its task window), a stripe the task window. The activity log runs along the bottom as a ticker (it pauses under the mouse). Dark only, big type; in the ten languages; `TestMission` walks through it with made-up activity.
- The mod is unchanged (0.12.0 is the project's version; `claude plugin update` isn't needed).

## v0.11.0 (2026-11-01)

- **Messenger, a third theme**: the sessions as coworkers in a messaging app (`/t/messenger/`, or the theme picker). The sidebar lists them with a face whose motion is the state (still when idle, breathing while it thinks, ticking while a tool runs, waving with a red ring while it waits for you, eyes shut off duty), a title line (model, effort, folder) and a progress line (the tool running, what it waits for, the last prompt); below them the tasks as group chats. The middle column holds the conversation (the employee window, embedded) or a group's team chat (the task window), a member's conversation one click from it and the way back. The right column is the profile: the computer (what runs now, what ran, "Take over" opens the terminal), the model, folder, repository and Claude Code version, and the figures (the context fill, the rate limits, the cost and today's, the tokens, the tool calls, the MCP servers, the subagents, the to-dos). Light or dark follows the system, the switch is remembered. In the ten languages; `TestMessenger` walks through it with made-up activity. The asks' cards rise over the input as everywhere (not inline in the flow yet), and the computer shows what ran and opens the terminal in a window: an in-page terminal view is still to come.
- The bridge no longer takes a subagent's model for the session's (`agent.start` carried one since 0.8.0, and the employee shrank to the subagent's size).
- Dark themes get a readable tool row and task chip in the employee window (`--tool-ink`).
- The mod is unchanged (0.11.0 is the project's version; `claude plugin update` isn't needed).

## v0.10.0 (2026-11-01)

- **The HQ console, a second theme**: a big company's management console (`/t/hq/`, or the theme picker): a KPI strip (headcount, online, working, waiting for you, today's cost, the average context fill, API errors), and five tabs: **Overview** (who waits for you, the activity of the last 30 minutes, today's cost by employee, tokens by model, the recent activity), **People** (the roster: state, model and effort, folder, project, context fill, tool calls, turns, today's cost, uptime; sortable, filtered by state chips and the search box; a row opens the employee window, Start work and Terminal at hand), **Approvals** (the pending asks as a queue of cards, answered there), **Projects** (the tasks as a board by status; a card opens the task window) and **Activity** (the bridge's activity log, filtered by person and kind). Light or dark follows the system, the switch at the top is remembered. In the ten languages; `TestHQ` walks through it with made-up activity.
- The shared pieces take the console's colors through `ui/ui.css`'s variables, flat and rounded there. The console redraws once per frame however many pushes come; it isn't measured under load yet (the performance tests drive the pixel office).
- The mod is unchanged (0.10.0 is the project's version; `claude plugin update` isn't needed).

## v0.9.0 (2026-11-01)

- **The protocol, written down**: `docs/protocol.md` says what the bridge gives the pages (the stream's messages, every object and its fields, what a page derives, the calls it makes), what the mod reports, and what a theme of the office page has to offer. The snapshot's `protocol` is 2: a task no longer carries `roomName`, and its `room` is an optional hint.
- **Themes**: the office page comes in themes, one folder each (`web/themes/<name>/` with a `theme.json` and an `index.html`), switched with the picker in the HUD (`/?theme=<name>` or `/t/<name>/`, remembered in a cookie; `GET /api/themes` lists them). The pixel office is the first and the default; it looks and behaves as before. New themes come in the next releases.
- **Shared pieces**: the bridge's client (`web/symphony.js`: the state as the bridge pushes it, and every call a page makes), the employee window, the launch dialog, the task dialog and window with the team chat (`web/ui/*.js`, with their look in `ui/ui.css`, restyled through CSS variables), and `i18n.js` loading a theme's own catalogs over the shared ones. A page that fell behind the message log now really fetches it again.
- **Tasks come loose from the meeting rooms**: the bridge no longer binds a task to a room (no "room busy", the cap is 2 to 5 members everywhere, the kickoff no longer names a room); the pixel office seats the tasks in its rooms itself, every browser the same way (the room a task was started from when it's free, else the first free one with seats enough, else the largest), and the HUD has a "New task" button besides the rooms' plates.
- The mod is unchanged (0.9.0 is the project's version; `claude plugin update` isn't needed).

## v0.8.0 (2026-11-01)

- **The mod reports everything the engine tells it about a session**, and the bridge keeps it for the pages (the pixel office shows little of it yet; the themes to come are designed on it, see `docs/plan-protocol-themes.md`): the engine's version, the mod's version, the git repository and the surface at the start; the context window's fill, the rate-limit windows and the cost (`session.measure`, coalesced to one report every 2 seconds, pushed to the pages as a `usage` message without a snapshot); each response's tokens and stop reason (summed by model in the session's `usage.totals`); why a turn ended (a refusal with the API's reason, an API error), subagents by name (type, description, model), the agent team's task list (`todos`), notifications, compactions, model switches, folder changes, every slash command, each tool call's duration and the reason it failed or was denied, the surfaces attached, the MCP servers connected, background tasks and scheduled runs, and why the session ended. `claude plugin update symphony-bridge@symphony`.
- The bridge keeps a **ledger** (`ledger.json`, 90 days): the cost, tokens, turns and tool calls of each account's sessions by day; the snapshot carries today's rows, `GET /api/ledger` every day kept. It also keeps an **activity log** of the last 500 things that happened (sessions coming and going, tool calls, asks and their outcomes, messages, errors, launches), `GET /api/activity`, so a page that opens late sees the same timeline.
- The snapshot carries `protocol: 1` (the version of what the bridge gives the pages) and `started` (when the bridge started).
- The employee window shows how long a tool call took, a failure's reason in the row's tooltip, the slash commands that ran, and notices for a refusal, an API error, a compaction, a model switch and the engine's notifications.
- A plan for the next versions, `docs/plan-protocol-themes.md`: the page protocol and theme framework (v0.9.0), then three themes.

## v0.7.1 (2026-11-01)

- The README now starts with a runbook for AI agents: paste "Install https://github.com/feynmanzcys-bytes/symphony for me" into Claude Code and it installs the program, the mod and the bridge at login, checking each step. The nine translations follow it.
- The mod (0.7.1): a session the bridge first refused as busy, or that started before the bridge was up, now listens for what the page sends (prompts, Stop) as soon as the bridge takes it, and after the bridge rejects the token nothing more is sent, not even heartbeats. The "busy" message says approvals go to the terminal for now. `claude plugin update symphony-bridge@symphony`.
- A task member's kickoff says what really happens to the branches: the lead merges the branches of its own repository, the bridge merges into the base branch only in a repository it made for the task, and members are asked not to edit the same files.
- Page texts: the "Start work" button is named the same everywhere, the member limits and the task id come from the bridge, the merge-conflict, ending and undelivered messages say what happened, the search box says it finds sessions by name too.
- Releases: running the workflow by hand never publishes, even on a tag; the dry run keeps the archives as an artifact.

## v0.7.0 (2026-10-31)

- **Collaborative tasks in the meeting rooms**: a click on a free small meeting room creates a task: write what has to be done, pick 2 to 5 members and start. Members are employees — each gets a second session just for the task, its own session stays as it was — and advisors, one-off participants made with the usual fields (name, folder, model, effort) and gone when the task ends. The first member picked leads by default (it splits the task, hands out the parts with SendMessage, reviews and merges); untick "lead" and everyone gets the whole task. The members sit in the meeting room for the duration; the room's nameplate shows the task; a click on the room opens the task window, where each member's chat is a click away and the task can be ended.
- **A worktree for everyone**: each member's session runs in its own git worktree on its own branch (`symphony/<task id>/<member>`, say `symphony/T1/bob`) of that member's folder, so members never step on each other's files and your checkout stays as it was. A folder that isn't a git repository becomes one for the task (`git init`, a commit of everything in it) and stays one; when the task ends the members' branches are merged into it, so the folder holds the results, and the branches are kept (a merge that fails is undone and the task says so; the work stays on the branches). In your own repositories nothing is merged: the branches stay for you to merge.
- **Team chat in the task window**: the messages the members send each other, each with the sender's pixel figure and name and `@who` it went to, and a box to write to the team yourself: `@bob-T1 …` reaches that member (several `@names` reach all of them; typing `@` offers the members to pick from), a message without `@` reaches everyone in the task. A member's own chat opens from the task window, docked beside it; a member's figure in the room opens the task window.
- An account remembers the folder its last session worked in, however that session was started, so an employee off duty can join a task there and "Start work" offers that folder.
- The mod is 0.7.0 (it reports the task a session belongs to): `claude plugin update symphony-bridge@symphony`.

## v0.6.1 (2026-10-31)

- Sessions started from the page no longer inherit the bridge's own Claude Code session (its messaging socket and session id): a page-started session is now a clean top-level session, as if launched from a plain terminal. Without this, when the bridge runs inside a Claude Code session (the mod can start it from one), the started sessions collided with it and SendMessage between them was never delivered.
- The employee window shows a model's thinking even when it carries no words (a model whose thinking is summarized): a folded "Thought for Ns" line instead of nothing, and the time it took once done.
- A finished answer bubble and tool rows no longer collapse to a sliver in the chat; blank lines around a fenced code block are trimmed; messages between sessions get a readable timestamp. The mod is 0.6.1: `claude plugin update symphony-bridge@symphony`.

## v0.6.0 (2026-10-31)

- **Every session as a chat**: a click on an employee opens its window in the middle of the page (it replaces the card on the right and the pending popup): the employee at the top, and below it the session as a chat: the prompts, the model's thinking (folded, "Thinking…" in orange with three dots while it goes on), its answers as they stream, the tool calls with their outcome, messages from other sessions in purple, and the asks with how they were settled. Write at the bottom and it reaches the session as your prompt (Enter sends, Shift+Enter breaks a line); Stop interrupts the running turn. The mod (0.6.0) streams the response, reports the prompts that enter and polls the bridge for what the page sends: `claude plugin update symphony-bridge@symphony`.
- **Asks in the employee's window**: permission requests and questions rise over the input of that employee's window as cards and must be handled before you can write; nothing pops up by itself any more. The red count in the bar at the top opens the first waiting employee's window.
- **No more windows, no tmux**: sessions started from the page run on a pseudo-terminal inside the bridge (`/dev/ptmx` on macOS and Linux, ConPTY on Windows): nothing opens on the screen and nothing takes your focus, and the bridge answers "trust this folder" on every platform. "Open terminal" in the employee's window opens a terminal window attached to the session (`symphony attach <id>` does the same anywhere; `Ctrl-]` or closing the window detaches, and the session goes on). The sessions are the bridge's children, so stopping the bridge ends them. `-terminal` is accepted and ignored.
- A new employee starts with everything allowed (`bypassPermissions`), Opus and the most thinking (`max`); an old one as it last worked.
- The activity log at the bottom left is a panel now, hidden until the bar's button opens it (the page remembers).
- Once a launch is online the new employee's window opens.

## v0.5.0 (2026-10-31)

- Lighter traffic between the bridge and the pages: a change pushes the message log no more (the first snapshot and `/api/state` carry it; new messages come as events, and a page that missed one fetches the log again), each push is encoded once for all pages, and a pending ask's long input strings reach the page cut to 4 KiB with a note. With 300 long messages a tool call used to send every page two snapshots of about 650 KiB.
- The office page does less per change: the building is laid out and its background drawn only when the seats, the window or the pixel size change (not on every event), the message panel and the employee card only when the messages change, name tags only when their text changes; it draws 30 frames a second, and a window drag lays out once per frame.
- The bridge keeps a failed mod check for 10 seconds, so opening the page doesn't run `claude plugin list` every time; the message log is written to disk in the background instead of while every other request waits; the pages' files answer with an ETag, so a reload downloads them only when they changed.
- The mod (0.5.0) reports events through a queue in the background, so a tool call no longer waits for two round trips to the bridge; a report that gets no answer in 5 seconds is given up, and after the bridge rejects the token nothing more is sent. `claude plugin update symphony-bridge@symphony`.

## v0.4.0 (2026-10-30)

- The office opens in your browser once the bridge is up (`-open=false` turns that off), and starting `symphony` again while it runs just opens the office.
- `symphony -autostart on` starts the bridge whenever you log in (a systemd user service on Linux, a launchd agent on macOS, the registry's Run key on Windows), and `symphony -autostart off` undoes it.
- A session started with `SYMPHONY_TOKEN` starts the bridge itself when nothing answers at its address on this machine (`symphony -background`, with `symphony` on your PATH), and the bridge keeps running after the session ends. This needs the mod at 0.4.0: `claude plugin update symphony-bridge@symphony`.
- `SYMPHONY_DATA` sets the default data folder.
- The pending popup hangs from the top of the window, so a new ask no longer moves the card you are about to click.
- The bar at the top no longer slides when the page opens with it put away.
- The archive names in the README and in the release notes link to their downloads.

## v0.3.0 (2026-10-30)

- First release: the bridge as a ready-made program, `symphony`, for Linux, macOS and Windows on x86-64 and ARM64, with `checksums.txt`. Go is now needed only to run the bridge from source.
- `symphony -version` prints the version, and the bridge's first log line shows it.
