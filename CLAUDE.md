# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal working rules (language, workflow) belong in `CLAUDE.local.md`, which is not checked in.

## What this is

symphony puts a team of Claude Code sessions into a pixel-art office web page: sessions show up as employees at their desks, each one's window shows its session as a chat (and takes prompts), and permission requests and AskUserQuestion questions are handled there. It is built independently, without borrowing from other repositories, and is not affiliated with Anthropic (the README says so, and the manifests' descriptions start with "Unofficial").

## Code

The bridge is Go (standard library only; the e2e tests also use chromedp), the mod is TypeScript (as Claude Code requires), the pages are plain JavaScript, and the office is Canvas 2D pixel art with no front-end libraries.

- **Accounts**: an identity is a name + a token + a fixed seat, and an account serves one session at a time (a second session gets 409 and falls back to the terminal). Claude logins are not managed here; sessions may share one. Accounts live in the data folder's `accounts.json` (with tokens, mode 0600), messages in `messages.json`, the page key in `key` (64 hex digits, mode 0600; a folder the bridge makes is 0700) next to `open.html` (see the bridge's guard below), `lock` (held by the bridge using the folder: one bridge per data folder) and `bridge.addr` (that bridge's host:port, 0600).
- `mods/symphony-bridge/`: the Claude Code mod (function hooks, tested with Claude Code 2.1.316; the API is marked EARLY ACCESS, so run the e2e tests after upgrading Claude Code). It finds its account by `SYMPHONY_TOKEN` and does nothing in sessions without one (no bridge contact, no messages, no approval changes); `tool.check` hands permission requests to the bridge and `tool.call` intercepts AskUserQuestion; it reports session events, the session name, messages between sessions, the model and thinking effort (`turn.step`), and a heartbeat every 15 seconds that carries what the start told (`login`, `model`, `effort` as last reported, `surface`, `engine`, `mod`, `repo`), so a bridge that restarted or meets the session through its heartbeat learns them; for the chat it streams the main loop's thinking and text (`turn.step`, batched every 150 ms as `chat.delta`, closed by `chat.stop`), reports the prompts that enter (`prompt.submit` → `chat.user`) and each tool call's main argument (`summary`), and long-polls `/api/inbox` for what the page sends: `say` goes in with `$.prompt.submit({asUser: true})` and is reported as `chat.sent`, or as `chat.dropped` with the reason (cut to 500 characters) when it doesn't enter (`{drop}` from a hook, a settings hook or the engine, or a failure), `abort` stops the running main turn with `$.turn.abort`; reports go out through a queue in the background (a hook never waits for the bridge; a report is given up after 5 seconds; the queue holds at most 500, past it the oldest heartbeat, usage report or streamed piece goes first, else the oldest report but a start or an end; each report carries the id of the session it happened in, and nothing is reported for a session after its end; none goes before `session.start`'s own, `startTold`: the engine runs its own start hooks inside `session.start`, where SessionStart reports the session's name, and a report that went first would seat a task member as a desk session); a bridge that took a request and didn't answer in time is left alone for 10 seconds: everything meant for it then is dropped at once (asks go to the terminal), until the pause ends or the late request gets its answer; the inbox poll starts with the first report the bridge accepts (so a session refused as busy at first, or started before the bridge, joins through its heartbeat), and after a 401 nothing more is sent, not even heartbeats. An `/api/event` answer with `fresh: true` (the bridge didn't know the session) makes the mod report the tools, the surfaces, the session's name and the background work again (not session.start, so a task member gets no second kickoff). Asks wait for the page in long polls of at most 25 s each (the bridge answers within 20 s; no answer means it is stuck, and the engine's own verdict stands); the terminal's interrupt (`next.signal`, Esc) ends the wait at once; anything but the page's own answer withdraws the card (`/api/cancel`, from a timer of the `session.start` hook's `$`: the engine cancels every request an interrupted dispatch starts afterwards, through any `$`; and even while the bridge is left alone), as does an ask the bridge takes only after the 10 s timeout, once its answer comes; the first ask in a process shows the `waiting` toast (the bridge's address; Esc cancels). After /clear (or a /resume or fork inside the session) the engine fires no `session.start`: `session.end` with reason `clear`/`resume` forgets the session id, and `classic.SessionStart` with source clear, resume or fork, only once that end was seen (`claude --resume` fires a resume right after its session.start), reports `session.start` under the new id with the start's info, restarts the heartbeat, reports the tools and starts the new id's own inbox poll at once. Besides the chat it reports everything else the engine tells it, for the pages to show as they like (every field optional, so older mods and bridges keep working): at the start the engine's version (`$.session.version`), its own version (`plugin.json`), the repository (`$.session.repo`: `root`, `name`, `internal`; never the remote, whose URL may carry credentials) and the surface, then the tools and MCP servers (`$.tool.list` → `session.tools`, again on `classic.ConfigChange`); the context window's fill, the rate limits and the cost (`session.measure` → `session.usage`, coalesced to one report per 2 s); each response's tokens and stop reason (the `stop` chunk of `turn.step`, on `chat.stop`); why a turn ended (`turn.complete`: `reason`, `refusal`, `tokens`) and API errors (`classic.StopFailure` → `turn.error`); subagents by name (`agent.spawn`, reported after `next` as the id is on the result → `agent.start`; `classic.SubagentStop` → `agent.end`); the agent team's task list (`classic.TaskCreated/TaskCompleted` → `todo.create/done`; "todo" because "task" is the office's collaborative task); notifications (`classic.Notification` → `session.notify`), compactions (`classic.PostCompact` → `session.compact`), model switches (`classic.PostModelSwitch` → `session.model` with `from` and `source`), folder changes (`classic.CwdChanged` → `session.cwd`, and every later event carries the new folder), every slash command (`command.run`), a tool call's duration (`$.clock.now` around `next` → `tool.end`'s `durationMs`) and the reason it failed or was denied (`classic.PostToolUseFailure/PermissionDenied` → `tool.fail`), the surfaces attached (`session.attach/detach` → `session.surfaces`), background tasks and scheduled runs (`classic.Stop` → `session.background`) and why the session ended (`session.end`'s `reason`). The login is only what `$.session.identity()` answers, and it answers only a mod the organization's managed settings installed (`{deny}` elsewhere), so for most people no login is reported and the pages' login chip stays empty; the mod reads no `.claude.json`, `CLAUDE_CONFIG_DIR`, `HOME` or `USERPROFILE`, and `$.fs.read` only its own `plugin.json` and the transcript (for `/rename`). The token goes only to a bridge that proved it knows it: before the first request that carries it, and again after any request that got no answer (the bridge may have stopped and something else taken the port), the mod sends `POST /api/hello` `{id: <hex SHA-256 of the token>, nonce: <16 random bytes in hex>}` with no token (5 s timeout; concurrent requests share one check; an HTTP error answer such as 409 keeps it while the inbox poll runs, and without one (a session refused as busy) the next report checks again) and wants `{proof}`, the HMAC-SHA256 of `"symphony-hello:" + nonce` keyed with the token (`hmacSha256`, exported for the tests; compared in either case): a 401 is the `badToken` toast, any other wrong answer (a wrong or missing proof, not JSON, a 404 from an older bridge, a 500) the `notBridge` toast, and either way nothing more is sent in that session. `SYMPHONY_BRIDGE` must be `http://127.0.0.1:<port>`, `http://localhost:<port>` or `http://[::1]:<port>` (a trailing slash ignored; `LOCAL_BRIDGE`) or any `https://` address; anything else is the `insecure` toast and the bridge is never contacted. A malformed answer from the page (not an object, a decision other than allow/deny, a reason that isn't a string, AskUserQuestion answers that aren't an object) leaves the engine's own verdict, so the terminal asks. When a bridge on this machine doesn't answer as the session starts, the mod starts it with `symphony -background` (the program on PATH; `SYMPHONY_DATA` tells it where the accounts are) and reports in again (not when something took the check and never answered: no bridge could start there; when symphony fails, the `startFailed` toast carries its last line, without the log's time or the page key, or its exit status). When the bridge is still unreachable, rejects the token, fails the check or the account is busy, it says so (a toast) and falls back to the terminal. Its few messages are in `hooks/messages.ts` (10 languages, picked by `SYMPHONY_LANG`, then `LC_ALL` / `LC_MESSAGES` / `LANG`); unit tests are in `tests/`; the folder also holds the mod's README.md and LICENSE (a copy of the repository's).

What can't be undone is in the bridge's log (`log.task_undo_failed`). A member's folder may not lie in another task's worktree (`task_dir_in_worktree`) or, when it would have to be made a repository, be the home folder, above it or a drive's root (`task_dir_home`; a home folder that already is a repository passes); a folder git can't tell about (a `.git` in it or above it that git can't read or won't trust: dubious ownership, a `.git` file pointing nowhere) is `task_git_failed` and never becomes a repository of its own; a remembered folder that is gone is `task_dir_missing`; a repository without a commit `task_repo_no_commit`; a folder inside a repository another running task made `task_repo_in_use`. - The bridge's guard (`ServeHTTP` in `server.go`, the rest in `key.go`; the launch endpoint runs commands on this machine): it listens on loopback only (`-addr`'s host must be `127.0.0.1`, `localhost` or `::1`, in `symphony attach` too, and its port a number from 1 to 65535; `localhost` is listened on and shown as `127.0.0.1`, so a browser can't end up on whoever holds `::1`; `0.0.0.0`, `::`, `:7788`, port 0, a LAN address or a hostname is `log.addr_not_local` and exit 1). Every answer carries the security headers (`Content-Security-Policy`: the bridge's own files only, no inline scripts, `frame-ancestors 'none'`; `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`). Then a `Host` that isn't this machine (DNS rebinding), a remote address that isn't loopback, a write whose `Origin` isn't this site, and (the mod's endpoints aside) an `/api/` request whose `Sec-Fetch-Site` is `cross-site` or `same-site` (a link or fetch from another site or port carries the Lax cookie, and even a GET does something: `/api/dirs` reads the folder it names, so it also refuses `Sec-Fetch-Mode: navigate`, a link opened from another app) are 403, and every request but the mod's (`modEndpoint`: `POST /api/event`, `/api/ask`, `/api/hello`, `/api/cancel/<id>`, `GET /api/inbox`, `/api/wait/<id>`, which keep the token check) must show the page key: the cookie `symphony_key_<port>` (the port from the request's Host; HttpOnly, SameSite=Lax, 400 days) or the header `X-Symphony-Key`. A GET or HEAD with the right `?key=` sets the cookie and redirects (303) to the same address without `key` (`signIn`; a wrong key counts as none); without the key `/api/*` is 401 `page_key`, `/`, `/t/<name>/` and `/approve` a 403 page in the bridge's language that says how to get in (`page_key.*`), any other file 401. The key (`LoadKey`: 32 random bytes in hex, made on the first start, kept across restarts, replaced when damaged; a key file others may read is made 0600, and when that fails (someone else's file) the bridge doesn't start; `ReadKey` for the programs that only talk to a bridge; `DefaultDataDir` lives here too) is also in the bridge's log, which prints the office as `<base>/?key=<key>` (`log.listening`, `already_running`, `background`, `background_slow`, `autostart_on`, `autostart_slow`, `open_failed`); deleting `key` signs every browser out at the next start. `POST /api/hello` is the mod's check (`hello`: the account whose token's SHA-256 is `id`, compared with every account in constant time; the answer is the HMAC over `"symphony-hello:" + nonce`), and the symphony program's (`id` the page key's SHA-256, the HMAC keyed with the key over `"symphony-page:" + nonce`; `ProveKey` is the client side); a body over 4 KiB, a badly formed id or nonce or an unknown id is 401 `token_invalid`. `docs/protocol.md` §1 and §6 have the details.
- `cmd/bridge` (releases ship it as the `symphony` program): it checks `-addr` (`localAddr`), loads the page key (`log.key_failed` and exit when it can't) and listens, then locks the data folder before reading anything there (`bridge.LockData`: `<data>/lock`, flock on macOS and Linux, a CreateFile that shares nothing on Windows, held while it runs; it notes its address in `bridge.addr`): when another bridge holds it (so it runs at another address), the program reads `bridge.addr`, and when this data folder's bridge proves it answers there opens that office (`-open`) and says so (`log.data_in_use`), else `log.data_locked`; exit 1 either way, nothing touched (`-background` reports `log.data_in_use` the same way when the copy it started exits so, `-autostart on` turns nothing on, and `-stop` stops the bridge `bridge.addr` names when none answers at `-addr`); when the address is taken it asks what answers there (`bridgeAt`, through `bridge.ProveKey`: `POST /api/hello` with the key's SHA-256 and a nonce, never the key; the answer has to be the HMAC of `"symphony-page:" + nonce` keyed with the key): this data folder's bridge (a second start, a double-click) → it opens that office and exits; anything else (another program, a bridge with another data folder, an older bridge without page keys) → `log.addr_taken`, exit 1, nothing opened (the same for `-background`; `-autostart on` checks before it turns anything on, and turns starting at login off again when something else takes the address while it waits). `symphony attach` and `cmd/demo` check the same way before their first request with the key (`log.key_unproven`). Otherwise it opens the office in the default browser once it's up (`-open`, on by default). on Linux, when the program that opens .html files (`xdg-mime query default text/html`) is a snap or a flatpak, `open.html` goes into that app's own folder instead (`~/snap/<snap>/common`, `~/.var/app/<app id>`; `ConfinedDir`), as such browsers can't read hidden folders of the home folder. `-background` starts a copy of itself detached from the terminal (`setsid`, or `DETACHED_PROCESS` on Windows; `detach_*.go`) with its log in `bridge.log` (0600) in the data folder, and returns once it answers (the copy runs in the data folder, or in the repository when started from it so the install hint still names it, `backgroundArgs`; it gets the flags rebuilt with absolute folders, `-data` always and `-open` kept, and not the starting session's `SYMPHONY_TOKEN/LAUNCH/TASK/BRIDGE`, `bridge.StripSessionEnv`); the key is in that log too, as in the systemd journal and `~/Library/Logs/symphony.log`. `cmd/demo` (creates demo accounts and made-up activity; ## Commands

- Start the bridge (from the repository root): `go run ./cmd/bridge` (`-addr`, `-data`, `-claude`, `-lang`, `-version`, `-autostart on|off`, `-background`, `-open=false` so restarts don't open a tab each time; add `-web web` when editing pages to serve them from disk, so a reload shows changes; add `-mod mods/symphony-bridge` when editing the mod, so page-started sessions get your copy with `--plugin-dir`; without claude, starting from the page is off). `-addr` takes only a `127.0.0.1`, `localhost` or `::1` host. `symphony attach [-addr host:port] [-data folder] <launch id>` shows a page-started session's terminal (`go run ./cmd/bridge attach <id>` from the repository). When this data folder's bridge already answers at 127.0.0.1:7788 (one started at login, say), `go run ./cmd/bridge` only opens its office and exits (a bridge with another data folder there stops it with `log.addr_taken`): stop that one first (`systemctl --user stop symphony` on Linux) or give the development bridge another `-addr` and a data folder of its own (`-data`): one bridge per data folder
- Start a session by hand: `printf 'X-Symphony-Key: %s\n' "$(cat ~/.config/symphony/key)" | curl -H @- -X POST localhost:7788/api/accounts -d '{"name":"someone"}'` for a token (the page key is in the data folder: `~/Library/Application Support/symphony/key` on macOS), then `SYMPHONY_TOKEN=<token> claude --name someone --permission-mode manual` (install the mod first, or add `--plugin-dir mods/symphony-bridge` when editing it; in auto mode most actions don't ask, so approvals never reach the page)
- Validate: `claude plugin validate .` (the marketplace) and `claude plugin validate mods/symphony-bridge`; mod unit tests: `claude plugin test mods/symphony-bridge`
- Unit tests: `go test -race ./...` (package bridge's TestMain gives git an empty global config, `GIT_CONFIG_GLOBAL`, and `GIT_CONFIG_NOSYSTEM=1`)
- Cross-compile check for the three platforms (after any Go change): `for os in windows darwin linux; do GOOS=$os go vet ./internal/... ./cmd/... && GOOS=$os go build -o /dev/null ./cmd/bridge; done`
- End-to-end (starts real sessions and spends tokens, about a minute): `SYMPHONY_E2E=1 go test -tags e2e -v -count=1 -timeout 20m ./e2e/`, screenshots in `e2e/artifacts/`; needs `claude`, `tmux` (for the sessions the tests drive themselves) and a browser (Chromium, or Google Chrome; `TestReconnect` checks the client's message log trimming, the connection banner and the open window's reload when the bridge comes back (the harness's `cutPages`), a hidden page letting its stream go, and a roster row pressed while it redraws (no tokens); `TestTask` walks through a collaborative task without tokens (claude is a script that sits there; the test reports the members in as the mod would): the task dialog from a click on a room, the git side (worktrees, branches, a plain folder made a repository and plain again), the kickoff prompts, the members seated in the room, the task window and a member's chat window, the end and the cleanup; `TestScreens` is a screenshot tour of every screen and state (the office in four pixel sizes and three window sizes, the rooms' plates, the task dialog's states, the task window, the member and employee windows, the HUD, the panels, `/approve`, in en, zh-CN and ja) into `e2e/artifacts/screens/`, failing on a page error, a missing locale key or a raw key on screen (no tokens); - CI (`.github/workflows/ci.yml`, GitHub-owned actions only, no secrets, a read-only token) runs on every push to dev and main, every pull request to them (forks included) and by hand (`workflow_dispatch`), docs-only changes aside (`**.md`, `docs/**`, `LICENSE`): gofmt, vet (also `-tags e2e ./e2e/`), unit tests, the builds for the three platforms, the mod's validation and unit tests with a pinned Claude Code (`CLAUDE_CODE_VERSION`, bump it with the tested version above), and `TestI18n` + `TestIdle` + `TestLayout` + `TestAsksDock` + `TestTask` + `TestScreens` + `TestThemesLoad` + `TestHQ` + `TestMessenger` + `TestMission` + `TestReconnect` in Chrome. `TestOffice` and `TestModStartsBridge` spend tokens and stay local. Look at the run after each push: `gh run list`, `gh run watch`. `.github/workflows/history.yml` checks the commit messages of every push and pull request, docs-only ones included (the whole history, `fetch-depth: 0`; it fails when a commit message has a line starting with `Claude-Session:`). `.github/dependabot.yml` opens weekly pull requests to dev for the actions and the Go modules.
- Releases (`.github/workflows/release.yml`): pushing a tag `vX.Y.Z` that is on main checks that it is `plugin.json`'s version (a suffix like `-rc.1` makes a pre-release), checks that `CHANGELOG.md` has a section for it (`.github/changelog.sh` prints it), runs the unit tests, builds the bridge as `symphony` for Linux, macOS and Windows on amd64 and arm64 (`.github/release.sh`: `-X main.version`, which `-version` and the log print; each archive holds the program, LICENSE and README.md; plus `checksums.txt`) and publishes them with `gh release create` (the notes: "What's new", the CHANGELOG section, then `.github/release-notes.md`, where `{tag}` becomes the tag, so its links point at that release's archives, then GitHub's generated notes). Archive names carry no version, so `releases/latest/download/<archive>` links stay valid. To release: bump `plugin.json` if it's still on the last release's version, write the version's section in `CHANGELOG.md` (`## vX.Y.Z (date)` and the changes as a list), bring dev to main, then `git tag -a vX.Y.Z -m vX.Y.Z` on main and `git push origin vX.Y.Z`. `.github/release.sh v0.0.0 /tmp/dist` builds the same archives locally; running the workflow by hand (`gh workflow run release.yml`, on a branch or a tag) is a dry run that keeps them as a workflow artifact for 7 days and publishes nothing.

## Branches and commits

`dev` is the development line; pull requests go to dev (`CONTRIBUTING.md`). `main` is the default branch on GitHub, which `--marketplace feynmanzcys-bytes/symphony` reads. Commit messages are in English and carry no `Claude-Session:` line (`history.yml` fails on one).
