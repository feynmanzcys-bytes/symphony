# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal working rules (language, workflow) belong in `CLAUDE.local.md`, which is not checked in.

## What this is

symphony puts a team of Claude Code sessions into an office web page: by default Coworkers (the messenger theme), where the sessions are coworkers in a messaging app, each one's conversation shows its session as a chat (and takes prompts), and permission requests and AskUserQuestion questions are handled there; the pixel office, where they are employees at their desks, is the other theme to pick (Settings → Theme). It is built independently, without borrowing from other repositories, and is not affiliated with Anthropic (the README says so, and the manifests' descriptions start with "Unofficial").

## Code

The bridge is Go (standard library only; the e2e tests also use chromedp), the mod is TypeScript (as Claude Code requires), the pages are plain JavaScript, and the office is Canvas 2D pixel art with no front-end libraries.

- **Accounts**: an identity is a name + a token + a fixed seat, and an account serves one session at a time (a second session gets 409 and falls back to the terminal). Claude logins are not managed here; sessions may share one. Accounts live in the data folder's `accounts.json` (with tokens, mode 0600), messages in `messages.json`, the bridge's own settings in `settings.json` (`settings.go`: `botHome`, the default folder for the employees' own folders, written only once set), the page key in `key` (64 hex digits, mode 0600; a folder the bridge makes is 0700) next to `open.html` (see the bridge's guard below), `lock` (held by the bridge using the folder: one bridge per data folder) and `bridge.addr` (that bridge's host:port, 0600).
- `mods/symphony-bridge/`: the Claude Code mod (function hooks, version 1.5.0, tested with Claude Code 2.1.317; the API is marked EARLY ACCESS, so run the e2e tests after upgrading Claude Code). It finds its account by `SYMPHONY_TOKEN` and does nothing in sessions without one (no bridge contact, no messages, no approval changes); once the session started it takes `SYMPHONY_TOKEN` out of the session's environment (`hideToken`: kept in the session's state, `$.state` `symphony-bridge.office`, declared in the mod's own contract `types/symphony-bridge.d.ts`, which `plugin.json` names; with the session id it was kept for and the office text the prompt got; a module reloaded by `/reload-plugins` (or a worker respawn), which the engine gives `session.start` again, reads it there and carries the session on (`revived`, `begin`'s `carryOn`: the page's rules and the office text stay, and it reports a heartbeat instead of a second `session.start`, so no start line and no kickoff; a reloaded module the engine gave no start starts its heartbeat with its first accepted report); `/clear` makes the state name the new session (`keepOffice`); when the state can't be written the environment keeps it), so the Bash commands, scripts and MCP servers the session starts afterwards don't inherit it (`SYMPHONY_LAUNCH` stays: the bridge finds a session's leftovers by it); `tool.check` hands permission requests to the bridge and `tool.call` intercepts AskUserQuestion; a permission it could keep for the rest of the session goes with the rule it proposes (`remember`; `suggestRule` in `hooks/rules.ts`: every file edit as one rule, a Bash command's first word (two for `npm test`, `git status` and the like), never a compound command, else the tool by its name), and the page's allow with `remember` keeps it (`$.state`, reported as `session.rule`): from then on `tool.check` allows what a kept rule covers (`ruleAllows`) without asking, only what the engine itself would have asked about, within the organization's ceiling (`e.ceiling`) and never over a plugin's verdict; an MCP server's form (`classic.Elicitation`) goes to the page as an `elicitation` ask, which only shows it: the terminal answers it, and `classic.ElicitationResult` settles the card (`POST /api/settle/<id>`; `turn.complete` settles leftovers as `cancel`); with `SYMPHONY_CONTEXT=1` (the launch dialog's office context; `sessionVars` strips it like the other session variables) `prompt.compose` adds a section to the system prompt, once per conversation, naming the session and the others online by the names SendMessage finds them by (`GET /api/roster`); it reports session events, the session name, messages between sessions, the model and thinking effort (`turn.step`), and a heartbeat every 15 seconds that carries what the start told (`login`, `model`, `effort` as last reported, `surface`, `engine`, `mod`, `repo`), so a bridge that restarted or meets the session through its heartbeat learns them; for the chat it streams the main loop's thinking and text (`turn.step`, batched every 150 ms as `chat.delta`, closed by `chat.stop`), reports the prompts that enter (`prompt.submit` → `chat.user`) and each tool call's main argument (`summary`), and long-polls `/api/inbox` for what the page sends (`ack=` names the last item it did, `inboxAck`; the bridge drops an item only then, `InboxItem.ID` counting up per session, so a poll cut off on its way back loses nothing): `say` goes in with `$.prompt.submit({asUser: true})` (the says of one poll together: submit resolves only once the engine took the prompt, after the running turn) and is reported as `chat.sent`, or as `chat.dropped` with the reason (cut to 500 characters) when it doesn't enter (`{drop}` from a hook, a settings hook or the engine, or a failure), `abort` stops the running main turn with `$.turn.abort`; reports go out through a queue in the background (a hook never waits for the bridge; a report is given up after 5 seconds; the queue holds at most 500, past it the oldest heartbeat, usage report or streamed piece goes first, else the oldest report but a start or an end; `session.end` goes to the front of the queue, so a backlog doesn't cut the goodbye off in the hook's 1.5 s; each report carries the id of the session it happened in, and nothing is reported for a session after its end; none goes before `session.start`'s own, `startTold`: the engine runs its own start hooks inside `session.start`, where SessionStart reports the session's name, and a report that went first would seat a task member as a desk session); a bridge that took a request and didn't answer in time is left alone for 10 seconds: everything meant for it then is dropped at once (asks go to the terminal), until the pause ends or the late request gets its answer; the inbox poll starts with the first report the bridge accepts (so a session refused as busy at first, or started before the bridge, joins through its heartbeat), and after a 401 nothing more is sent, not even heartbeats. An `/api/event` answer with `fresh: true` (the bridge didn't know the session) makes the mod report the tools, the surfaces, the session's name and the background work again (not session.start, so a task member gets no second kickoff). Asks wait for the page in long polls of at most 25 s each (the bridge answers within 20 s; no answer means it is stuck, and the engine's own verdict stands); the terminal's interrupt (`next.signal`, Esc) ends the wait at once; anything but the page's own answer withdraws the card (`/api/cancel`, from a timer of the `session.start` hook's `$`: the engine cancels every request an interrupted dispatch starts afterwards, through any `$`; and even while the bridge is left alone), as does an ask the bridge takes only after the 10 s timeout, once its answer comes; the first ask in a process shows the `waiting` toast (the bridge's address; Esc cancels). After /clear (or a /resume or fork inside the session) the engine fires no `session.start`: `session.end` with reason `clear`/`resume` forgets the session id, and `classic.SessionStart` with source clear, resume or fork, only once that end was seen (`claude --resume` fires a resume right after its session.start), reports `session.start` under the new id with the start's info, restarts the heartbeat, reports the tools and starts the new id's own inbox poll at once. Besides the chat it reports everything else the engine tells it, for the pages to show as they like (every field optional, so older mods and bridges keep working): at the start the engine's version (`$.session.version`), its own version (`plugin.json`), the repository (`$.session.repo`: `root`, `name`, `internal`; never the remote, whose URL may carry credentials) and the surface, then the tools and MCP servers (`$.tool.list` → `session.tools`, again on `classic.ConfigChange`); the context window's fill, the rate limits and the cost (`session.measure` → `session.usage`, coalesced to one report per 2 s); each response's tokens and stop reason (the `stop` chunk of `turn.step`, on `chat.stop`); why a turn ended (`turn.complete`: `reason`, `refusal`, `tokens`) and API errors (`classic.StopFailure` → `turn.error`); subagents by name (`agent.spawn`, reported after `next` as the id is on the result → `agent.start`; `classic.SubagentStop` → `agent.end`); the agent team's task list (`classic.TaskCreated/TaskCompleted` → `todo.create/done`; "todo" because "task" is the office's collaborative task); notifications (`classic.Notification` → `session.notify`), compactions (`classic.PostCompact` → `session.compact`), model switches (`classic.PostModelSwitch` → `session.model` with `from` and `source`), folder changes (`classic.CwdChanged` → `session.cwd`, and every later event carries the new folder), every slash command (`command.run`), a tool call's duration (`$.clock.now` around `next` → `tool.end`'s `durationMs`) and the reason it failed or was denied (`classic.PostToolUseFailure/PermissionDenied` → `tool.fail`), the surfaces attached (`session.attach/detach` → `session.surfaces`), background tasks and scheduled runs (`classic.Stop` → `session.background`) and why the session ended (`session.end`'s `reason`). The login is only what `$.session.identity()` answers, and it answers only a mod the organization's managed settings installed (`{deny}` elsewhere), so for most people no login is reported and the pages' login chip stays empty; the mod reads no `.claude.json`, `CLAUDE_CONFIG_DIR`, `HOME` or `USERPROFILE`, and `$.fs.read` only its own `plugin.json` and the transcript (for `/rename`). The token goes only to a bridge that proved it knows it: before the first request that carries it, and again after any request that got no answer (the bridge may have stopped and something else taken the port), the mod sends `POST /api/hello` `{id: <hex SHA-256 of the token>, nonce: <16 random bytes in hex>}` with no token (5 s timeout; concurrent requests share one check; an HTTP error answer such as 409 keeps it while the inbox poll runs, and without one (a session refused as busy) the next report checks again) and wants `{proof}`, the HMAC-SHA256 of `"symphony-hello:" + nonce` keyed with the token (`hmacSha256`, exported for the tests; compared in either case): a 401 is the `badToken` toast, any other wrong answer (a wrong or missing proof, not JSON, a 404 from an older bridge, a 500) the `notBridge` toast, and either way nothing more is sent in that session. `SYMPHONY_BRIDGE` must be `http://127.0.0.1:<port>`, `http://localhost:<port>` or `http://[::1]:<port>` (a trailing slash ignored; `LOCAL_BRIDGE`) or any `https://` address; anything else is the `insecure` toast and the bridge is never contacted. A malformed answer from the page (not an object, a decision other than allow/deny, a reason that isn't a string, AskUserQuestion answers that aren't an object) leaves the engine's own verdict, so the terminal asks. When a bridge on this machine doesn't answer as the session starts, the mod starts it with `symphony -background` (the program on PATH, run in the mod's own folder, `cwd: $.plugin.root`, never the session's; `SYMPHONY_DATA` tells it where the accounts are; when there's no `symphony` on PATH, it downloads the release of its own version in the background, `hooks/download.ts`: curl over https only, the archive's SHA-256 checked against that release's `checksums.txt` with sha256sum / shasum / certutil, unpacked with tar into `bin/` in the mod's folder (git-ignored), then started from there and reported in again; the `fetching` toast says so first and `fetchFailed` says why it couldn't; `SYMPHONY_DOWNLOAD=0` turns it off; once per process) and reports in again (not when something took the check and never answered: no bridge could start there; when symphony fails, the `startFailed` toast carries its last line, without the log's time or the page key, or its exit status). When the bridge is still unreachable, rejects the token, fails the check or the account is busy, it says so (a toast) and falls back to the terminal. Its few messages are in `hooks/messages.ts` (10 languages, picked by `SYMPHONY_LANG`, then `LC_ALL` / `LC_MESSAGES` / `LANG`); unit tests are in `tests/`; the folder also holds the mod's README.md and LICENSE (a copy of the repository's).

- `cmd/bridge` (releases ship it as the `symphony` program): it checks `-addr` (`localAddr`), loads the page key (`log.key_failed` and exit when it can't) and listens, then locks the data folder before reading anything there (`bridge.LockData`: `<data>/lock`, flock on macOS and Linux, a CreateFile that shares nothing on Windows, held while it runs; it notes its address in `bridge.addr`): when another bridge holds it (so it runs at another address), the program reads `bridge.addr`, and when this data folder's bridge proves it answers there opens that office (`-open`) and says so (`log.data_in_use`), else `log.data_locked`; exit 1 either way, nothing touched (`-background` reports `log.data_in_use` the same way when the copy it started exits so, `-autostart on` turns nothing on, and `-stop` stops the bridge `bridge.addr` names when none answers at `-addr`); when the address is taken it asks what answers there (`bridgeAt`, through `bridge.ProveKey`: `POST /api/hello` with the key's SHA-256 and a nonce, never the key; the answer has to be the HMAC of `"symphony-page:" + nonce` keyed with the key): this data folder's bridge (a second start, a double-click) → it opens that office and exits; anything else (another program, a bridge with another data folder, an older bridge without page keys) → `log.addr_taken`, exit 1, nothing opened (the same for `-background`; `-autostart on` checks before it turns anything on, and turns starting at login off again when something else takes the address while it waits). `symphony attach` and `cmd/demo` check the same way before their first request with the key (`log.key_unproven`). `ConfinedDir`), as such browsers can't read hidden folders of the home folder. `-background` starts a copy of itself detached from the terminal (`setsid`, or `DETACHED_PROCESS` on Windows; `detach_*.go`) with its log in `bridge.log` (0600) in the data folder, and returns once it answers (the copy runs in the data folder, or in the repository when started from it so the install hint still names it, `backgroundArgs`; - Releases (`.github/workflows/release.yml`): pushing a tag `vX.Y.Z` that is on main checks that it is `plugin.json`'s version (a suffix like `-rc.1` makes a pre-release), checks that `CHANGELOG.md` has a section for it (`.github/changelog.sh` prints it), runs the unit tests, builds the bridge as `symphony` for Linux, macOS and Windows on amd64 and arm64 (`.github/release.sh`: `-X main.version`, which `-version` and the log print; each archive holds the program, LICENSE and README.md; plus `checksums.txt`; reproducible: every file gets the commit's time (`SOURCE_DATE_EPOCH` when set), fixed permissions, and GNU tar records owner 0 with `gzip -n`, so rebuilding a release's commit on Linux gives its checksums), attests their build provenance (`actions/attest`: one SLSA provenance attestation for every archive and `checksums.txt`, signed through Sigstore's public log, before the release is published and never in a dry run; only that job has `id-token: write` and `attestations: write`; `gh attestation verify <archive> --repo feynmanzcys-bytes/symphony` checks one: exit status 0, silent outside a terminal) and publishes them with `gh release create` (the notes: "What's new", the CHANGELOG section, then `.github/release-notes.md`, where `{tag}` becomes the tag, so its links point at that release's archives, then GitHub's generated notes). Change the formula and the manifest in `packages.sh` (every release writes them again); `TestPackages` (`cmd/bridge/packages_test.go`) compares its output for made-up checksums with `cmd/bridge/testdata/packages`. `-autostart on` names the symphony PATH finds when it is this very program through a link (`stableExe`: Homebrew's `bin/symphony`, which an upgrade moves to the new version's folder), and on Windows the program's path as it runs, never resolved (`realExe`: Scoop's `apps\symphony\current` is a folder junction, which `filepath.EvalSymlinks` fails on and an update points at the new version), so the login entry survives an upgrade.
