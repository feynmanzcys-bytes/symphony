# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal working rules (language, workflow) belong in `CLAUDE.local.md`, which is not checked in.

## What this is

symphony puts a team of Claude Code sessions into a pixel-art office web page: sessions show up as employees at their desks, each one's window shows its session as a chat (and takes prompts), and permission requests and AskUserQuestion questions are handled there. It is built independently, without borrowing from other repositories.

## Code

The bridge is Go (standard library only; the e2e tests also use chromedp), the mod is TypeScript (as Claude Code requires), the pages are plain JavaScript, and the office is Canvas 2D pixel art with no front-end libraries.

- **Accounts**: an identity is a name + a token + a fixed seat, and an account serves one session at a time (a second session gets 409 and falls back to the terminal). Claude logins are not managed here; sessions may share one. Accounts live in the data folder's `accounts.json` (with tokens, mode 0600), messages in `messages.json`.
- `mods/symphony-bridge/`: the Claude Code mod (function hooks, tested with Claude Code 2.1.316; the API is marked EARLY ACCESS, so run the e2e tests after upgrading Claude Code). It finds its account by `SYMPHONY_TOKEN` and does nothing in sessions without one (no bridge contact, no messages, no approval changes); `tool.check` hands permission requests to the bridge and `tool.call` intercepts AskUserQuestion; it reports session events, the session name, messages between sessions, the model and thinking effort (`turn.step`), and a heartbeat every 15 seconds; for the chat it streams the main loop's thinking and text (`turn.step`, batched every 150 ms as `chat.delta`, closed by `chat.stop`), reports the prompts that enter (`prompt.submit` → `chat.user`) and each tool call's main argument (`summary`), and long-polls `/api/inbox` for what the page sends: `say` goes in with `$.prompt.submit({asUser: true})` and is reported as `chat.sent`, `abort` stops the running main turn with `$.turn.abort`; reports go out through a queue in the background (a hook never waits for the bridge, and a report is given up after 5 seconds); the inbox poll starts with the first report the bridge accepts (so a session refused as busy at first, or started before the bridge, joins through its heartbeat), and after a 401 nothing more is sent, not even heartbeats. Besides the chat it reports everything else the engine tells it, for the pages to show as they like (every field optional, so older mods and bridges keep working): at the start the engine's version (`$.session.version`), its own version (`plugin.json`), the repository (`$.session.repo`) and the surface, then the tools and MCP servers (`$.tool.list` → `session.tools`, again on `classic.ConfigChange`); the context window's fill, the rate limits and the cost (`session.measure` → `session.usage`, coalesced to one report per 2 s); each response's tokens and stop reason (the `stop` chunk of `turn.step`, on `chat.stop`); why a turn ended (`turn.complete`: `reason`, `refusal`, `tokens`) and API errors (`classic.StopFailure` → `turn.error`); subagents by name (`agent.spawn`, reported after `next` as the id is on the result → `agent.start`; `classic.SubagentStop` → `agent.end`); the agent team's task list (`classic.TaskCreated/TaskCompleted` → `todo.create/done`; "todo" because "task" is the office's collaborative task); notifications (`classic.Notification` → `session.notify`), compactions (`classic.PostCompact` → `session.compact`), model switches (`classic.PostModelSwitch` → `session.model` with `from` and `source`), folder changes (`classic.CwdChanged` → `session.cwd`, and every later event carries the new folder), every slash command (`command.run`), a tool call's duration (`$.clock.now` around `next` → `tool.end`'s `durationMs`) and the reason it failed or was denied (`classic.PostToolUseFailure/PermissionDenied` → `tool.fail`), the surfaces attached (`session.attach/detach` → `session.surfaces`), background tasks and scheduled runs (`classic.Stop` → `session.background`) and why the session ended (`session.end`'s `reason`). `$.session.identity()` answers `{deny}` to a mod the organization didn't install, so the login email still comes from `.claude.json`. When a bridge on this machine doesn't answer as the session starts, the mod starts it with `symphony -background` (the program on PATH; `SYMPHONY_DATA` tells it where the accounts are) and reports in again. When the bridge is still unreachable, rejects the token or the account is busy, it says so and falls back to the terminal. Its few messages are in `hooks/messages.ts` (10 languages, picked by `SYMPHONY_LANG`, then `LC_ALL` / `LC_MESSAGES` / `LANG`); unit tests are in `tests/`.
- Installing the mod: the repository root's `.claude-plugin/marketplace.json` is a plugin marketplace named `symphony`; `claude plugin install symphony-bridge --marketplace <local repository path or feynmanzcys-bytes/symphony>` installs it at user scope, so every session loads it. With a local path as the marketplace, sessions read that folder directly (mod edits apply to the next session or after `/reload-plugins`); a GitHub install is a copy, so bump the version in `plugin.json` and run `claude plugin update`. Bump the version whenever the mod's behavior changes. It is also the version of the whole project: each release's tag is `v` + this version (see Releases below).
- `internal/bridge/`: `hub.go` is the state hub (45 seconds without a heartbeat means off duty; every change pushes an event and a snapshot to the pages, encoded once for all of them; only the first snapshot and `/api/state` carry the message log, later ones name the latest message (`messageTail`) and new messages come as `message` events; a pending ask's long input strings reach the page cut to 4 KiB, `inputTruncated`; the message log is written to disk in the background, `Flush` waits for it; the snapshot carries `protocol` (1; the version of what the bridge gives the pages: additions keep it, a removed or renamed field raises it) and `started`), `usage.go` what the mod reports besides the state and the chat (`Session.Engine/Mod/Repo/Surface/Surfaces/Usage/Turns/Compactions/Todos/BgTasks/BgCrons/ToolCount/MCP/ToolMs/LastError/EndReason/Notify`, `Agent.Type/Description/Model/Background`; `session.usage` updates `Session.Usage` and goes to the pages as a `usage` push without a snapshot, and `chat.stop`'s tokens add up by model in `Usage.Totals`; the ledger, `ledger.json`: cost (the difference between the session's running total and the last report), tokens, turns and tool calls by account and day, 90 days kept, today's rows in the snapshot and all of them at `GET /api/ledger`; the activity log, the last 500 lines of what happened (`start`, `end`, `tool`, `ask`, `settled`, `message`, `error`, `launch`, `launchFailed`) at `GET /api/activity`), `chat.go` each session's chat log (the last 400 items: prompts, streamed thinking and text blocks, tool calls with their duration (`ms`) and the reason they failed (`text`), slash commands (`command`; not when the bubble just before is that command typed), messages, asks and notices (`text` is the code the page translates, `chat.notice.<code>`: `ended`, `aborted`, `refused`, `error`, `compacted`, `modelSwitched`, `notify`; `summary` a detail shown after it); pushed to the pages as `chat` events without a snapshot, a whole item or a `delta` to append; `/api/chat/<session>` gives the log) and the inbox the page fills (`/api/say`, `/api/abort`) and the mod drains (`/api/inbox`, a long poll that counts as a heartbeat), `accounts.go` accounts and seats, `server.go` HTTP (long polling for the mod, SSE for the pages), `server_chat.go` the chat and terminal endpoints, `launch.go` starting sessions, `term.go` the terminals the bridge hosts (a page-started session runs on a clean top-level environment: `childEnv` strips the bridge's own `CLAUDE_CODE_*` / `CLAUDECODE` / `CLAUDE_PID`, so sessions don't collide with the one that started the bridge and SendMessage between them works; `Term`: a child on a pseudo-terminal, its output kept in a 256 KiB history and fanned out to attached clients, keystrokes written back; `Terms` by launch id), `pty_*.go` how each platform makes one (`/dev/ptmx` on macOS and Linux, ConPTY on Windows), `terminal.go` the `Terminal` backend around them (`ptyTerminal`, which also answers "trust this folder" and fails a launch whose process exits) and `Window`, which opens a terminal window on this machine running `symphony attach`, `errors.go` errors with codes.
- Errors the page may show carry a code: the API answers `{error: <English>, code, params}` and the page translates `error.<code>`; a failed launch keeps `errorCode` / `errorParams` in the snapshot. Go error strings stay English.
- `internal/autostart/`: starting the bridge at login (`-autostart on|off`): a systemd user service on Linux (`KillMode=process`; the sessions are the bridge's children now, so stopping the bridge ends them; PATH as it was when turned on), a launchd agent on macOS (log in `~/Library/Logs/symphony.log`), a value under the registry's Run key on Windows (a console window). The bridge started at login gets the flags given with `-autostart on` (folders made absolute, `-data` always) and `-open=false`; `-autostart` refuses a `go run` build. Linux and macOS are tested for real (`TestAutostart`); Windows has unit tests.
- `internal/i18n/`: language detection (`-lang`, `SYMPHONY_LANG`, `LC_ALL` / `LC_MESSAGES` / `LANG`) and the bridge's own translations (`locales/<lang>.json`: log lines and flag help).
- Three platforms, one way: sessions started from the page run on a pseudo-terminal inside the bridge, nothing opens on the screen, and the bridge answers "trust this folder". `symphony attach [-addr host:port] <launch id>` (`cmd/bridge/attach.go`, raw mode in `raw_*.go`) shows a session's terminal in the current one: it streams `/api/terminal/<id>/stream` (the history first), posts keystrokes to `/input` and sizes to `/resize`; `Ctrl-]` or closing the window detaches. The employee window's "Open terminal" (`POST /api/terminal/<id>/open`) opens a window running that command: Terminal.app on macOS (a one-off script that deletes itself), a graphical terminal on Linux (needs `DISPLAY` or `WAYLAND_DISPLAY`), a new console on Windows (`terminal_windows.go`). Stopping the bridge (SIGINT/SIGTERM) kills its sessions. `-terminal` is accepted and ignored (older `-autostart` entries). The data folder is `SYMPHONY_DATA`, else it comes from `os.UserConfigDir()`: `~/.config/symphony`, `~/Library/Application Support/symphony`, `%AppData%\symphony` (on Windows mode 0600 has no effect; the user folder's permissions protect the tokens).
- `web/`: `office.html` (`/`, the pixel office), `approve.html` (`/approve`, a simpler approval page), `asks.js` (the ask cards both share), `i18n.js` (language choice, `t()`, the language picker) and `locales/<lang>.json` (the pages' translations), all built into the bridge binary.
- Translations: 10 languages (en, zh-CN, zh-TW, ja, ko, es, fr, de, pt-BR, ru), English is the fallback. Every catalog has the same keys as its `en.json` and the same `{placeholders}`, which `go test ./internal/i18n/` checks. User-visible text never sits in code: the pages use `t('key')` or `data-i18n`, the bridge's log lines use `i18n.T`, and the bridge sends codes to the page. Code comments are English.
- The employee window (`office.html`, "the employee window"): a click on an employee opens a centered modal (`#chat`, up to 1100 px wide): the head (name, state dot and line, chips: seat, model and effort, session name, folder, subagents, tool calls, login; buttons: open terminal while the session has a launch id, stop while it works, start work and delete while off duty), the flow (the chat log, fetched from `/api/chat/<session>` when the window opens or the session changes, then kept up by `chat` events: `user` items are dark bubbles on the right (`queued` dimmed until the mod reports `chat.sent`), `text` white on the left, `thinking` a folded `<details>` with an orange "Thinking" and three dots until done, `tool` a one-line monospace row colored by its outcome, `message` purple (lighter and on the right when this employee sent it), `ask` a gray line with the outcome, `notice` centered; fenced code, `code` and **bold** are the only markup), and the dock (the textarea, Enter sends to `/api/say/<session>`, Shift+Enter breaks a line; while the session has pending asks the dock becomes an overlay hanging from 42% of the window's height with the cards (`asks.js`) over the hidden input, so a new card goes in below and never moves the one being clicked). Nothing opens by itself when an ask arrives: the employee and the HUD's pending chip turn red, and the chip opens the first waiting employee's window. The activity log is a panel at the bottom left, hidden until the HUD's button opens it (remembered). The launch dialog's defaults for a new employee: `bypassPermissions`, `opus`, `max`; once the launch is online, the new employee's window opens.
- The office: one floor of a big company's building (no reception): the open office in the middle (rows of 6 desks, at least 3 rows, full rows even for a small team, more rows as it grows), small meeting rooms for 3 to 5 on its left (rows on both sides of halls off the corridor beside it; nameplates named after musical forms, `room.small.N`; only UI for now, for meetings in a later version), a glass meeting room (its door faces the corridor) and a lounge (counter, fridge, vending machine, foosball, a TV in front of the sofa, a round table, a water cooler) on its right; people come and go by the lifts in the back wall, and the printer and a bookshelf stand in the strip below the desks. The building fills the window (`layout`, `fitScreen`): the scale is the biggest at which the smallest building for the team fits (whole device pixels from 2 up; a fractional scale is drawn at the next whole one and smoothed down), and the HUD's pixel size steps draw that same building finer (`detail`: the finer steps draw D pixels to a pixel of the office, as many as the screen has, at most 5 and a whole share of them, so nothing is resampled; thin lines as hairlines and people moving by finer steps, then shadows and rounded corners, then floor textures, wood grain and reflections; `hair`, `ground`, `box`, remembered); spare height adds rows of desks (centered in the office), spare width goes to both sides equally so the office stays in the middle, and once the lounge is tall, rows of small meeting rooms go below it; each account has a fixed desk; state colors are idle green, working yellow, waiting for an approval or answer red, off duty gray; size follows the model (haiku < sonnet < opus < fable), muscles follow the effort (a red headband at max); messages between sessions get a flying envelope, a bubble and the message log. The page draws 30 frames a second; `layout` (and the background) is redone only when the seats, the "+", the window or the pixel size change (`layoutKey`), name tags are rewritten only when their text changes, and the message panel only when the messages change (`messagesVersion`).
- Idle life (`office.html`, "idle life"): an idle employee stays at its desk for 20 seconds (phone or games), then wanders: TV on the lounge sofa, coffee, the vending machine, the water cooler, a window, the bookshelf, the printer, or in pairs foosball, tag or a chat at the round table; from 2.5 minutes it naps (mostly hiding in the meeting room) and wakes now and then. It all counts from the session's `stateSince`, and pairs form on the clock, so a reload changes nothing. Work or a pending ask sends it back to its desk; so does a click on it (its window opens too), and then it stays there until its next turn. Employees walk on a small graph of walkways and spots (`buildPlaces`); away from the desk the name tag shows just the name and moves out of the way of other tags. The HUD is a bar at the top in the middle, in the same pixel style, over a plain band of the back wall: the logo and title, the search box, which finds employees by name, session name or folder (`/` focuses it; picking one is the same as clicking it), chips with the counts by state (a click lights those employees up, a second click or Esc lets go; while asks wait, the pending chip turns red and opens the first waiting employee's window), the message log, the activity log, new employee, the pixel size and the language picker; the tab under it slides it up out of the way and back (down by default, the page remembers; while it's up, the tab shows how many asks wait), and the side panels start below it.
- Starting sessions from the page: the "+" on an empty desk hires a new employee; "Start work" in an off-duty employee's window brings them back (last folder and options filled in, same seat). The bridge starts claude on a pseudo-terminal of its own (`Terms`, by launch id) in that folder with the account's token, the bridge's address and the page's language (`SYMPHONY_LANG`), plus `TERM`/`COLORTERM` when unset; the mod is the installed one (`-mod` development mode adds `--plugin-dir`); the bridge answers "trust this folder" for new folders and fails the launch when the process exits (the last lines of its screen are in the error). The bridge checks the mod with `claude plugin list --json` (`Mod` in `launch.go`); without it, starting from the page is off and the page shows the install command (reload after installing, no bridge restart; the answer is kept for 10 seconds, a good one for a minute).
- Tasks (`internal/bridge/task.go`, `git.go`, `server_task.go` with the task endpoints, `startTask` and the git preparation; the page's "task dialog" and "task window"): a click on a free small meeting room creates a collaborative task, a team of 2 to 5 sessions (at most the room's seats) on one description. Members are employees (each gets a second, task-only session; its desk session is untouched; an employee is in at most one running task) and advisors (one-off accounts made with the launch form's fields, `Advisor: true`, seat -1, deleted when the task ends). Ids are `T` + a counter (`tasks.json`, which also keeps the last 200 tasks); a member's session name is `<account name>-<task id>` (`bob-T7`), its branch `symphony/<task id>/<slug>` (the slug of the account name; a second member with the same slug gets `-2`, `-3`), its worktree `<folder>/.symphony/worktrees/<slug>-<task id>` (listed in `.git/info/exclude`). Every member works in its own git worktree on its own branch of its folder (an employee's: its desk session's cwd, else its last launch folder, else the last folder a desk session reported, `Account.Dir`; an advisor's: the one entered). A folder that is no git repository is made one (`git init` + a commit of everything, `Inited`) and stays one: when the task ends the members' branches are merged into its base branch, so the folder holds the result, and `.git` and the branches are kept (a merge that fails is undone, the branches stay and the task ends `failed`, `task_merge_conflict`); in the user's own repositories nothing is merged, only the worktrees go and the branches stay. The sessions are started like launches (`Launch.Task`, `SYMPHONY_TASK` in the environment; the mod reports it in every event as `task`; `Session.Task`), and the one-session-per-account rule holds per (account, task). When a member reports in, the bridge sends it a kickoff prompt (`task.kickoff.*` in the bridge's locales, in the page's language) that names the team (SendMessage finds them by name), the branches and the rules: with a lead (the first member, by default) the lead splits the task and merges at the end, the others wait for its assignments; without one ("flat") everyone gets the task. A task ends from the task window or when its last session ends (a member whose process exits or whose launch fails counts as gone); the cleanup (kill the terminals with their process groups, commit uncommitted work on the branches — a detached HEAD's commits go to `<branch>-detached` —, remove the worktrees and empty `.symphony` folders, merge the members' branches of inited repositories into their base (only those: a `-detached` branch or branches a member made stay unmerged, kept for the user), drop the members' launch and terminal records, delete the advisors of an `ended` task) runs in the background, one task at a time per directory tree (`treeLocks`; a git command times out after 5 minutes); a failed task keeps its members' sessions and advisors for its window until it is forgotten; a bridge start ends the tasks it finds running. A member's folder may not lie in another task's worktree (`task_dir_in_worktree`) or, when it would have to be made a repository, be the home folder, above it or a drive's root (`task_dir_home`; a home folder that already is a repository passes); a remembered folder that is gone is `task_dir_missing`; a repository without a commit `task_repo_no_commit`; a folder inside a repository another running task made `task_repo_in_use`. A member that starts a fresh session again (`/clear`) gets the kickoff again (a new session with the same launch id replaces the old one even before its end is reported); an account that is a member of a task still shown can't be deleted; task numbers are never reused; the message log keeps the newest 300 messages of each task still shown besides 300 others; a session that reports in without `task` (an older mod) takes it from its launch. API: `GET/POST /api/tasks`, `POST /api/tasks/<id>/end`, `DELETE /api/tasks/<id>` (a failed one); the task chat: `POST /api/tasks/<id>/say` `{text}` sends to every member online, or with leading `@<member session name>`s (`@bob-T7`; each the longest member name that matches, followed by the end, whitespace or `:` `,` `：` `，`, which is dropped; names may hold spaces) only to the members named that are online (`missed` lists the named ones that were offline; an `@` that matches no member is plain text for everyone, unless it reads like `<name>-<task id>`, which is `task_say_unknown_member`), as their next prompt from the page (`sayLocked`), and logs one `Message` with no sender (`origin: page`, `toNames` the members named, `toName` them joined by spaces, `to` the session when one is named; `task_say_unknown_member`, `session_offline`, `task_ended`); `GET /api/tasks/<id>/chat` is the log's messages of the task; every `Message` carries `task`, the sender's task, else the receiver's (empty between desks); the snapshot carries `tasks` (running, ending, failed) and a `task` event. The task window's "Team chat" lists the task's messages (`Message.Task`): a member's as a purple bubble with its pixel figure and the sender's name, the text starting with `@<toNames>`; the user's as dark bubbles on the right ("You"); the input below sends through `POST /api/tasks/<id>/say` (leading `@name` mentions, several allowed, pick the members; none means everyone online; typing `@` opens a picker of the members above the input: arrows, Enter/Tab or a click insert the name; Enter sends, Shift+Enter breaks a line). A member's figure in the room isn't a way to its chat: a click on it opens the task window, and a member's chat opens only from there (`openMember`): docked to the right of the task window, the pair centered side by side (`#chat.docked`, from 1250 px wide; narrower windows stack it over the task window), one member at a time, its row highlighted; the HUD's pending chip, the search box and the desk window's "Open <member>" button go the same way for task sessions. On the page the members sit at the room's table (the employee's desk shows an empty chair, its monitor lit by the desk session), the nameplate's light goes yellow (red while a member waits) and shows the task id, the task window lists the members (a click opens that member's chat window) and ends the task.
- The bridge only accepts this machine's Host and refuses writes that other sites send through the browser (the launch endpoint runs commands on this machine). The pages have no login yet; don't bind to a non-local address.
- `cmd/bridge` (releases ship it as the `symphony` program): it listens first, and when a bridge already answers at `-addr` (a second start, a double-click) it just opens that office and exits; otherwise it opens the office in the default browser once it's up (`-open`, on by default; `BrowserCommand` in `internal/bridge/browser.go`: `xdg-open` only with a graphical session, `open`, `rundll32`). `-background` starts a copy of itself detached from the terminal (`setsid`, or `DETACHED_PROCESS` on Windows; `detach_*.go`) with its log in `bridge.log` in the data folder, and returns once it answers. `cmd/demo` (creates demo accounts and made-up activity). `e2e/`: end-to-end acceptance with real Claude sessions.

## Commands

- Start the bridge (from the repository root): `go run ./cmd/bridge` (`-addr`, `-data`, `-claude`, `-lang`, `-version`, `-autostart on|off`, `-background`, `-open=false` so restarts don't open a tab each time; add `-web web` when editing pages to serve them from disk, so a reload shows changes; add `-mod mods/symphony-bridge` when editing the mod, so page-started sessions get your copy with `--plugin-dir`; without claude, starting from the page is off). `symphony attach <launch id>` shows a page-started session's terminal (`go run ./cmd/bridge attach <id>` from the repository). When a bridge already answers at 127.0.0.1:7788 (one started at login, say), `go run ./cmd/bridge` only opens its office and exits: stop that one first (`systemctl --user stop symphony` on Linux) or give the development bridge another `-addr`
- Start a session by hand: `curl -X POST localhost:7788/api/accounts -d '{"name":"someone"}'` for a token, then `SYMPHONY_TOKEN=<token> claude --name someone --permission-mode manual` (install the mod first, or add `--plugin-dir mods/symphony-bridge` when editing it; in auto mode most actions don't ask, so approvals never reach the page)
- Validate: `claude plugin validate .` (the marketplace) and `claude plugin validate mods/symphony-bridge`; mod unit tests: `claude plugin test mods/symphony-bridge`
- Unit tests: `go test -race ./...`
- Cross-compile check for the three platforms (after any Go change): `for os in windows darwin linux; do GOOS=$os go vet ./internal/... ./cmd/... && GOOS=$os go build -o /dev/null ./cmd/bridge; done`
- End-to-end (starts real sessions and spends tokens, about a minute): `SYMPHONY_E2E=1 go test -tags e2e -v -count=1 -timeout 20m ./e2e/`, screenshots in `e2e/artifacts/`; needs `claude`, `tmux` (for the sessions the tests drive themselves) and a browser (Chromium, or Google Chrome; `SYMPHONY_E2E_BROWSER` picks one, e.g. `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; `SYMPHONY_E2E_MODEL`, default `sonnet`, is the model of the real sessions); page-started sessions run on the bridge's pseudo-terminals, so it runs on Linux and macOS and skips on Windows. `TestOffice` gives sessions this repository's mod with `--plugin-dir`, or the installed one with `SYMPHONY_E2E_MOD=installed` (install it first), handles the asks in the employees' windows, checks A's chat, and talks to the page-started employee through its window; `TestInstall` walks through installing in a throwaway `CLAUDE_CONFIG_DIR` (no tokens, the real config stays untouched); `TestI18n` opens the pages in every language with made-up activity (no tokens; `SYMPHONY_E2E_LANGS=en,zh-CN` limits the languages); `TestIdle` walks through the idle life and the search box with made-up sessions, moving the page's clock forward instead of waiting (no tokens); `TestLayout` checks that the building fills windows of a few sizes with the open office in the middle and the small meeting rooms (3 to 5 seats, nameplates) on its left, the HUD's tab and the pixel size steps (no tokens); `TestAsksDock` checks that an employee window's asks cover the input and that a new ask leaves the card being clicked where it is (no tokens); `TestTask` walks through a collaborative task without tokens (claude is a script that sits there; the test reports the members in as the mod would): the task dialog from a click on a room, the git side (worktrees, branches, a plain folder made a repository and plain again), the kickoff prompts, the members seated in the room, the task window and a member's chat window, the end and the cleanup; `TestScreens` is a screenshot tour of every screen and state (the office in four pixel sizes and three window sizes, the rooms' plates, the task dialog's states, the task window, the member and employee windows, the HUD, the panels, `/approve`, in en, zh-CN and ja) into `e2e/artifacts/screens/`, failing on a page error, a missing locale key or a raw key on screen (no tokens); `TestPerfTasks` measures the page with 8 to 12 running tasks and 40+ members streaming (frame gaps, per-frame cost, snapshot and push sizes, heap), the bridge's task creation and cleanup on tiny and 5,000-file folders, and 200 create/end cycles for leaks (no tokens, about 3 minutes); `TestPerf` drives the page with heavy made-up streaming (one busy window, then 30 sessions at once) and fails on a page error or a frozen frame (no tokens); `TestAutostart` turns starting at login on and off with this machine's systemd or launchd, under a name of its own (Linux and macOS, no tokens, only with `SYMPHONY_E2E=1`); `TestModStartsBridge` starts a real session with a token while no bridge runs, and checks that the mod starts one with the symphony program built for the test, that the session takes its seat there and that the bridge outlives the session.
- CI (`.github/workflows/ci.yml`, GitHub-owned actions only) runs on every push to dev and main (and by hand, `workflow_dispatch`), docs-only pushes aside (`**.md`, `docs/**`, `LICENSE`): gofmt, vet (also `-tags e2e ./e2e/`), unit tests, the builds for the three platforms, the mod's validation and unit tests with a pinned Claude Code (`CLAUDE_CODE_VERSION`, bump it with the tested version above), and `TestI18n` + `TestIdle` + `TestLayout` + `TestAsksDock` + `TestTask` + `TestScreens` in Chrome. `TestOffice` spends tokens and stays local. The repo can't require checks (private on GitHub Free), so look at the run after each push: `gh run list`, `gh run watch`.
- Releases (`.github/workflows/release.yml`): pushing a tag `vX.Y.Z` that is on main checks that it is `plugin.json`'s version (a suffix like `-rc.1` makes a pre-release), checks that `CHANGELOG.md` has a section for it (`.github/changelog.sh` prints it), runs the unit tests, builds the bridge as `symphony` for Linux, macOS and Windows on amd64 and arm64 (`.github/release.sh`: `-X main.version`, which `-version` and the log print; each archive holds the program, LICENSE and README.md; plus `checksums.txt`) and publishes them with `gh release create` (the notes: "What's new", the CHANGELOG section, then `.github/release-notes.md`, where `{tag}` becomes the tag, so its links point at that release's archives, then GitHub's generated notes). Archive names carry no version, so `releases/latest/download/<archive>` links stay valid. To release: bump `plugin.json` if it's still on the last release's version, write the version's section in `CHANGELOG.md` (`## vX.Y.Z (date)` and the changes as a list), bring dev to main, then `git tag -a vX.Y.Z -m vX.Y.Z` on main and `git push origin vX.Y.Z`. `.github/release.sh v0.0.0 /tmp/dist` builds the same archives locally; running the workflow by hand (`gh workflow run release.yml`, on a branch or a tag) is a dry run that keeps them as a workflow artifact for 7 days and publishes nothing. While the repo is private, only collaborators can download releases.
