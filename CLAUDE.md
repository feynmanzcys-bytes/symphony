# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal working rules (language, workflow) belong in `CLAUDE.local.md`, which is not checked in.

## What this is

symphony puts a team of Claude Code sessions into a pixel-art office web page: permission requests and AskUserQuestion questions are handled in the page, and sessions show up as employees at their desks. It is built independently, without borrowing from other repositories.

## Code

The bridge is Go (standard library only; the e2e tests also use chromedp), the mod is TypeScript (as Claude Code requires), the pages are plain JavaScript, and the office is Canvas 2D pixel art with no front-end libraries.

- **Accounts**: an identity is a name + a token + a fixed seat, and an account serves one session at a time (a second session gets 409 and falls back to the terminal). Claude logins are not managed here; sessions may share one. Accounts live in the data folder's `accounts.json` (with tokens, mode 0600), messages in `messages.json`.
- `mods/symphony-bridge/`: the Claude Code mod (function hooks, tested with Claude Code 2.1.314; the API is marked EARLY ACCESS, so run the e2e tests after upgrading Claude Code). It finds its account by `SYMPHONY_TOKEN` and does nothing in sessions without one (no bridge contact, no messages, no approval changes); `tool.check` hands permission requests to the bridge and `tool.call` intercepts AskUserQuestion; it reports session events, the session name, messages between sessions, the model and thinking effort (`turn.step`), and a heartbeat every 15 seconds; reports go out through a queue in the background (a hook never waits for the bridge, and a report is given up after 5 seconds), and after a 401 nothing more is sent. When a bridge on this machine doesn't answer as the session starts, the mod starts it with `symphony -background` (the program on PATH; `SYMPHONY_DATA` tells it where the accounts are) and reports in again. When the bridge is still unreachable, rejects the token or the account is busy, it says so and falls back to the terminal. Its few messages are in `hooks/messages.ts` (10 languages, picked by `SYMPHONY_LANG`, then `LC_ALL` / `LC_MESSAGES` / `LANG`); unit tests are in `tests/`.
- Installing the mod: the repository root's `.claude-plugin/marketplace.json` is a plugin marketplace named `symphony`; `claude plugin install symphony-bridge --marketplace <local repository path or feynmanzcys-bytes/symphony>` installs it at user scope, so every session loads it. With a local path as the marketplace, sessions read that folder directly (mod edits apply to the next session or after `/reload-plugins`); a GitHub install is a copy, so bump the version in `plugin.json` and run `claude plugin update`. Bump the version whenever the mod's behavior changes. It is also the version of the whole project: each release's tag is `v` + this version (see Releases below).
- `internal/bridge/`: `hub.go` is the state hub (45 seconds without a heartbeat means off duty; every change pushes an event and a snapshot to the pages, encoded once for all of them; only the first snapshot and `/api/state` carry the message log, later ones name the latest message (`messageTail`) and new messages come as `message` events; a pending ask's long input strings reach the page cut to 4 KiB, `inputTruncated`; the message log is written to disk in the background, `Flush` waits for it), `accounts.go` accounts and seats, `server.go` HTTP (long polling for the mod, SSE for the pages), `launch.go` starting sessions, `terminal*.go` how each platform opens a terminal, `errors.go` errors with codes.
- Errors the page may show carry a code: the API answers `{error: <English>, code, params}` and the page translates `error.<code>`; a failed launch keeps `errorCode` / `errorParams` in the snapshot. Go error strings stay English.
- `internal/autostart/`: starting the bridge at login (`-autostart on|off`): a systemd user service on Linux (`KillMode=process`, so stopping it leaves the sessions' tmux running; PATH as it was when turned on), a launchd agent on macOS (log in `~/Library/Logs/symphony.log`), a value under the registry's Run key on Windows (a console window). The bridge started at login gets the flags given with `-autostart on` (folders made absolute, `-data` always) and `-open=false`; `-autostart` refuses a `go run` build. Only Linux is tested for real (`TestAutostart`); macOS and Windows have unit tests.
- `internal/i18n/`: language detection (`-lang`, `SYMPHONY_LANG`, `LC_ALL` / `LC_MESSAGES` / `LANG`) and the bridge's own translations (`locales/<lang>.json`: log lines and flag help).
- Three platforms: Windows (a new console window runs claude directly, `terminal_windows.go`), macOS (Terminal.app by default, running a one-off script that deletes itself; `-terminal tmux` for tmux), Linux (tmux when installed, a graphical terminal otherwise). Only tmux can answer "trust this folder"; with a window backend the first start in a new folder needs a click. The data folder is `SYMPHONY_DATA`, else it comes from `os.UserConfigDir()`: `~/.config/symphony`, `~/Library/Application Support/symphony`, `%AppData%\symphony` (on Windows mode 0600 has no effect; the user folder's permissions protect the tokens).
- `web/`: `office.html` (`/`, the pixel office), `approve.html` (`/approve`, a simpler approval page), `asks.js` (the ask cards both share), `i18n.js` (language choice, `t()`, the language picker) and `locales/<lang>.json` (the pages' translations), all built into the bridge binary.
- Translations: 10 languages (en, zh-CN, zh-TW, ja, ko, es, fr, de, pt-BR, ru), English is the fallback. Every catalog has the same keys as its `en.json` and the same `{placeholders}`, which `go test ./internal/i18n/` checks. User-visible text never sits in code: the pages use `t('key')` or `data-i18n`, the bridge's log lines use `i18n.T`, and the bridge sends codes to the page. Code comments are English.
- The office: one floor of a big company's building (no reception): the open office in the middle (rows of 6 desks, at least 3 rows, full rows even for a small team, more rows as it grows), small meeting rooms for 3 to 5 on its left (rows on both sides of halls off the corridor beside it; nameplates named after musical forms, `room.small.N`; only UI for now, for meetings in a later version), a glass meeting room (its door faces the corridor) and a lounge (counter, fridge, vending machine, foosball, a TV in front of the sofa, a round table, a water cooler) on its right; people come and go by the lifts in the back wall, and the printer and a bookshelf stand in the strip below the desks. The building fills the window (`layout`, `fitScreen`): the scale is the biggest at which the smallest building for the team fits (whole device pixels from 2 up; a fractional scale is drawn at the next whole one and smoothed down), and the HUD's pixel size steps draw that same building finer (`detail`: the finer steps draw D pixels to a pixel of the office, as many as the screen has, at most 5 and a whole share of them, so nothing is resampled; thin lines as hairlines and people moving by finer steps, then shadows and rounded corners, then floor textures, wood grain and reflections; `hair`, `ground`, `box`, remembered); spare height adds rows of desks (centered in the office), spare width goes to both sides equally so the office stays in the middle, and once the lounge is tall, rows of small meeting rooms go below it; each account has a fixed desk; state colors are idle green, working yellow, waiting for an approval or answer red, off duty gray; size follows the model (haiku < sonnet < opus < fable), muscles follow the effort (a red headband at max); messages between sessions get a flying envelope, a bubble and the message log; pending asks open a popup and are handled right there (it hangs from the top, so a new card goes in below and never moves the one being clicked). The page draws 30 frames a second; `layout` (and the background) is redone only when the seats, the "+", the window or the pixel size change (`layoutKey`), name tags are rewritten only when their text changes, and the message panel and the employee card only when the messages change (`messagesVersion`).
- Idle life (`office.html`, "idle life"): an idle employee stays at its desk for 20 seconds (phone or games), then wanders: TV on the lounge sofa, coffee, the vending machine, the water cooler, a window, the bookshelf, the printer, or in pairs foosball, tag or a chat at the round table; from 2.5 minutes it naps (mostly hiding in the meeting room) and wakes now and then. It all counts from the session's `stateSince`, and pairs form on the clock, so a reload changes nothing. Work or a pending ask sends it back to its desk; so does a click on it (its card opens too), and then it stays there until its next turn. Employees walk on a small graph of walkways and spots (`buildPlaces`); away from the desk the name tag shows just the name and moves out of the way of other tags. The HUD is a bar at the top in the middle, in the same pixel style, over a plain band of the back wall: the logo and title, the search box, which finds employees by name, session name or folder (`/` focuses it; picking one is the same as clicking it), chips with the counts by state (a click lights those employees up, a second click or Esc lets go; while asks wait, the pending chip turns red and opens them), the message log, new employee, the pixel size and the language picker; the tab under it slides it up out of the way and back (down by default, the page remembers; while it's up, the tab shows how many asks wait), and the side panels start below it.
- Starting sessions from the page: the "+" on an empty desk hires a new employee; "Start work" on an off-duty employee's card brings them back (last folder and options filled in, same seat). The bridge starts claude in a tmux session (`sym-<id>`) in that folder with the account's token, the bridge's address and the page's language (`SYMPHONY_LANG`); the mod is the installed one (`-mod` development mode adds `--plugin-dir`); the bridge answers "trust this folder" for new folders. The bridge checks the mod with `claude plugin list --json` (`Mod` in `launch.go`); without it, starting from the page is off and the page shows the install command (reload after installing, no bridge restart; the answer is kept for 10 seconds, a good one for a minute).
- The bridge only accepts this machine's Host and refuses writes that other sites send through the browser (the launch endpoint runs commands on this machine). The pages have no login yet; don't bind to a non-local address.
- `cmd/bridge` (releases ship it as the `symphony` program): it listens first, and when a bridge already answers at `-addr` (a second start, a double-click) it just opens that office and exits; otherwise it opens the office in the default browser once it's up (`-open`, on by default; `BrowserCommand` in `internal/bridge/browser.go`: `xdg-open` only with a graphical session, `open`, `rundll32`). `-background` starts a copy of itself detached from the terminal (`setsid`, or `DETACHED_PROCESS` on Windows; `detach_*.go`) with its log in `bridge.log` in the data folder, and returns once it answers. `cmd/demo` (creates demo accounts and made-up activity). `e2e/`: end-to-end acceptance with real Claude sessions.

## Commands

- Start the bridge (from the repository root): `go run ./cmd/bridge` (`-addr`, `-data`, `-claude`, `-terminal auto|tmux|window`, `-lang`, `-version`, `-autostart on|off`, `-background`, `-open=false` so restarts don't open a tab each time; add `-web web` when editing pages to serve them from disk, so a reload shows changes; add `-mod mods/symphony-bridge` when editing the mod, so page-started sessions get your copy with `--plugin-dir`; without claude or a usable terminal, starting from the page is off). When a bridge already answers at 127.0.0.1:7788 (one started at login, say), `go run ./cmd/bridge` only opens its office and exits: stop that one first (`systemctl --user stop symphony` on Linux) or give the development bridge another `-addr`
- Start a session by hand: `curl -X POST localhost:7788/api/accounts -d '{"name":"someone"}'` for a token, then `SYMPHONY_TOKEN=<token> claude --name someone --permission-mode manual` (install the mod first, or add `--plugin-dir mods/symphony-bridge` when editing it; in auto mode most actions don't ask, so approvals never reach the page)
- Validate: `claude plugin validate .` (the marketplace) and `claude plugin validate mods/symphony-bridge`; mod unit tests: `claude plugin test mods/symphony-bridge`
- Unit tests: `go test -race ./...`
- Cross-compile check for the three platforms (after any Go change): `for os in windows darwin linux; do GOOS=$os go vet ./internal/... ./cmd/... && GOOS=$os go build -o /dev/null ./cmd/bridge; done`
- End-to-end (starts real sessions and spends tokens, about a minute): `SYMPHONY_E2E=1 go test -tags e2e -v -count=1 -timeout 20m ./e2e/`, screenshots in `e2e/artifacts/`; needs `claude`, `tmux` and a browser (Chromium, or Google Chrome; `SYMPHONY_E2E_BROWSER` picks one); the e2e always uses the tmux backend, so it runs on Linux and on macOS with tmux, and skips on Windows. `TestOffice` gives sessions this repository's mod with `--plugin-dir`, or the installed one with `SYMPHONY_E2E_MOD=installed` (install it first); `TestInstall` walks through installing in a throwaway `CLAUDE_CONFIG_DIR` (no tokens, the real config stays untouched); `TestI18n` opens the pages in every language with made-up activity (no tokens; `SYMPHONY_E2E_LANGS=en,zh-CN` limits the languages); `TestIdle` walks through the idle life and the search box with made-up sessions, moving the page's clock forward instead of waiting (no tokens); `TestLayout` checks that the building fills windows of a few sizes with the open office in the middle and the small meeting rooms (3 to 5 seats, nameplates) on its left, the HUD's tab and the pixel size steps (no tokens); `TestAsksPopup` checks that a new ask leaves the card being clicked where it is (no tokens); `TestAutostart` turns starting at login on and off with this machine's systemd, under a unit name of its own (Linux, no tokens, only with `SYMPHONY_E2E=1`); `TestModStartsBridge` starts a real session with a token while no bridge runs, and checks that the mod starts one with the symphony program built for the test, that the session takes its seat there and that the bridge outlives the session.
- CI (`.github/workflows/ci.yml`, GitHub-owned actions only) runs on every push to dev and main, docs-only pushes aside: gofmt, vet, unit tests, the builds for the three platforms, the mod's validation and unit tests with a pinned Claude Code (`CLAUDE_CODE_VERSION`, bump it with the tested version above), and `TestI18n` + `TestIdle` + `TestLayout` + `TestAsksPopup` in Chrome. `TestOffice` spends tokens and stays local. The repo can't require checks (private on GitHub Free), so look at the run after each push: `gh run list`, `gh run watch`.
- Releases (`.github/workflows/release.yml`): pushing a tag `vX.Y.Z` that is on main checks that it is `plugin.json`'s version (a suffix like `-rc.1` makes a pre-release), checks that `CHANGELOG.md` has a section for it (`.github/changelog.sh`, which also puts it at the top of the notes as "What's new"), runs the unit tests, builds the bridge as `symphony` for Linux, macOS and Windows on amd64 and arm64 (`.github/release.sh`: `-X main.version`, which `-version` and the log print; each archive holds the program, LICENSE and README.md; plus `checksums.txt`) and publishes them with `gh release create` (notes start with `.github/release-notes.md`, where `{tag}` becomes the tag, so its links point at that release's archives). Archive names carry no version, so `releases/latest/download/<archive>` links stay valid. To release: bump `plugin.json` if it's still on the last release's version, write the version's section in `CHANGELOG.md` (`## vX.Y.Z (date)` and the changes as a list), bring dev to main, then `git tag -a vX.Y.Z -m vX.Y.Z` on main and `git push origin vX.Y.Z`. `.github/release.sh v0.0.0 /tmp/dist` builds the same archives locally; running the workflow by hand (`gh workflow run release.yml`) is a dry run that keeps them as a workflow artifact for 7 days. While the repo is private, only collaborators can download releases.
- See the office with made-up activity: start a second bridge (`-addr 127.0.0.1:7799 -data /tmp/x`), then `go run ./cmd/demo -base http://127.0.0.1:7799`

## Branches and commits

`dev` is the development line. `main` is the default branch on GitHub, which `--marketplace feynmanzcys-bytes/symphony` reads. Commit messages are in English.
