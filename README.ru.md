symphony — независимый проект. Он не связан с Anthropic, не одобрен и не спонсируется Anthropic. Claude и Claude Code — товарные знаки Anthropic, PBC.

Рассадите команду сеансов Claude Code по пиксельному офису: сразу видно, кто работает, а кто ждёт вас. С каждым можно поговорить в его собственном окне, а на запросы разрешений и вопросы AskUserQuestion ответить там же в один клик.

![Пиксельный офис: сотрудники за своими столами в рабочем зале, слева небольшие переговорные, справа переговорная и зона отдыха](docs/office.png)

У страницы две темы: пиксельный офис выше и **Коллеги** — сессии как коллеги в мессенджере, их лица показывают, чем они заняты, разговор в центре, профиль и компьютер справа. Выберите тему в настройках; bridge её запомнит.

## Установка

Быстрее всего так: откройте Claude Code и вставьте

> Установи мне https://github.com/feynmanzcys-bytes/symphony

Claude Code прочитает этот README и выполнит шаги из следующего раздела; перед любым изменением, которое останется и после установки, он спросит вас. Чтобы установить вручную, выполните те же шаги.

### Для AI-агентов: инструкция по установке

Вы читаете это, потому что пользователь попросил вас установить symphony. Выполните шаги ниже по порядку, в оболочке, и закончите отчётом из шага 6. Обычные решения (архив, папка в `PATH`) принимайте сами, но спрашивайте пользователя перед любым изменением, которое останется после этой установки: запуском symphony при каждом входе в систему, правкой rc-файла оболочки или изменением `PATH` пользователя. Перечислите все решения в отчёте.

У symphony две части, и нужны обе:

1. **Программа `symphony`** (bridge): один исполняемый файл, локальный веб-сервер на `http://127.0.0.1:7788/`, который отдаёт страницу офиса и запускает сеансы. Её стоит положить в `PATH` пользователя под именем `symphony`, потому что mod запускает её командой `symphony -background`, когда сеанс не находит работающий bridge.
2. **Плагин `symphony-bridge`** (mod): плагин Claude Code из маркетплейса этого репозитория, установленный на уровне пользователя. Он действует только в сеансах, запущенных с `SYMPHONY_TOKEN`, и ничего не делает во всех остальных.

#### Шаг 1: проверьте машину

```bash
uname -sm                 # Linux/macOS: по нему выбирается архив ниже (x86_64 → amd64; arm64/aarch64 → arm64)
claude --version          # нужен Claude Code 2.1.x (проверено на 2.1.316)
git --version             # только для совместных задач; если его нет, отметьте это в отчёте, но не останавливайтесь
symphony -version         # уже установлен? выводит "symphony v1.4.0 (darwin/arm64)"
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:7788/api/state   # bridge уже работает? 401: symphony 1.x; 200: более старый; 000: никакого
claude plugin list --json # mod уже установлен? ищите запись с "id": "symphony-bridge@symphony"
brew --version            # есть Homebrew (macOS, Linux)? тогда шаг 2 может установить через него
```

В Windows используйте PowerShell: `$env:PROCESSOR_ARCHITECTURE` равно `AMD64` или `ARM64`, а `scoop --version` отвечает, если установлен Scoop.

Если `claude` нет, остановитесь и скажите пользователю сначала установить Claude Code. Если и программа, и mod уже на месте, переходите к разделу «Обновление» ниже. Если на месте только одно из двух, выполните шаги для другого: шаги 2 и 3 для программы (если только `symphony -version` уже не выводит последний релиз), шаг 4 для mod, затем шаг 5. Уже работающий bridge остаётся на той программе, с которой был запущен: если он работает, вы остановите его перед шагом 5.

#### Шаг 2: получите программу

**Через Homebrew или Scoop.** Этот репозиторий — ещё и tap для Homebrew и bucket для Scoop. Если на шаге 1 нашёлся Homebrew (macOS, Linux) или Scoop (Windows), можно установить через него вместо остальной части этого шага и шага 3: он скачивает архив последнего релиза, сверяет его с SHA-256 из formula или manifest (их записали из `checksums.txt` релиза, когда тот вышел) и кладёт `symphony` в `PATH`. Затем переходите к шагу 4 и укажите в отчёте, через что установили.

```bash
brew tap feynmanzcys-bytes/symphony https://github.com/feynmanzcys-bytes/symphony
brew install symphony
symphony -version          # выводит версию и платформу
```

```powershell
scoop bucket add symphony https://github.com/feynmanzcys-bytes/symphony
scoop install symphony
symphony -version
```

Иначе скачайте архив для этой машины и `checksums.txt` релиза в новую, отдельную папку и проверьте архив, прежде чем что-либо устанавливать. Архивы называются `symphony_<os>_<arch>.tar.gz`, где `<os>` — `linux` или `darwin` (macOS), а `<arch>` — `amd64` или `arm64`, и `symphony_windows_<arch>.zip`.

В Linux и macOS:

```bash
d=$(mktemp -d)   # новая папка, которую можете читать только вы
echo "$d"        # запомните её: шаг 3 устанавливает из неё
cd "$d"
curl -fsSLO https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/symphony_<os>_<arch>.tar.gz
curl -fsSLO https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/checksums.txt
if command -v sha256sum >/dev/null; then sha256sum -c --ignore-missing checksums.txt; else shasum -a 256 -c --ignore-missing checksums.txt; fi   # должно вывести "symphony_<os>_<arch>.tar.gz: OK"
tar xzf symphony_<os>_<arch>.tar.gz              # теперь программа лежит в "$d/symphony"
```

Если проверка не вывела `OK`, остановитесь: не устанавливайте программу и сообщите пользователю. Если вместо curl используете `gh`, скачайте файлы в `$d` (gh сам создаст папку, если её ещё нет), затем выполните там ту же проверку и `tar`:

```bash
gh release download -R feynmanzcys-bytes/symphony -p 'symphony_<os>_<arch>.tar.gz' -p checksums.txt -D "$d"
```

В Windows, в PowerShell:

```powershell
$arch = if ($env:PROCESSOR_ARCHITECTURE -eq 'ARM64') { 'arm64' } else { 'amd64' }
$zip = "symphony_windows_$arch.zip"
$d = Join-Path $env:TEMP ("symphony-" + [guid]::NewGuid())   # новая папка
New-Item -ItemType Directory -Path $d | Out-Null
$url = 'https://github.com/feynmanzcys-bytes/symphony/releases/latest/download'
Invoke-WebRequest -UseBasicParsing -Uri "$url/$zip" -OutFile (Join-Path $d $zip)
Invoke-WebRequest -UseBasicParsing -Uri "$url/checksums.txt" -OutFile (Join-Path $d 'checksums.txt')
$want = ((Select-String -SimpleMatch -Path (Join-Path $d 'checksums.txt') -Pattern $zip).Line -split '\s+')[0]
$got = (Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path $d $zip)).Hash
if ($got -ne $want) { throw "checksum mismatch: $zip" } else { 'checksum OK' }
```

Затем, если установлен `gh` и выполнен вход (`gh auth status` проходит успешно), проверьте, где собран архив: у каждого архива релиза есть аттестация GitHub о том, что его собрал workflow релизов этого репозитория. Вне терминала `gh` ничего не выводит, если проверка прошла, поэтому смотрите на код возврата:

```bash
gh attestation verify "$d/symphony_<os>_<arch>.tar.gz" --repo feynmanzcys-bytes/symphony && echo 'attestation OK'
```

```powershell
gh attestation verify (Join-Path $d $zip) --repo feynmanzcys-bytes/symphony
if ($LASTEXITCODE -eq 0) { 'attestation OK' }
```

У релизов до v1.2.0 аттестации нет (`no attestations found`); для них достаточно проверки SHA-256. При любой другой ошибке остановитесь, как при неудачной проверке SHA-256. Если `gh` нет или вход не выполнен, пропустите эту проверку и укажите это в отчёте.

**Из исходников** в Linux или macOS, если пользователь предпочитает так (Go 1.27 или новее). Соберите исполняемый файл; `go run` не подойдёт, потому что `-autostart` отказывается работать со сборкой через `go run`:

```bash
d=$(mktemp -d)
git clone https://github.com/feynmanzcys-bytes/symphony.git "$d/src"
cd "$d/src" && go build -o "$d/symphony" ./cmd/bridge   # теперь программа лежит в "$d/symphony", как после распаковки архива
```

| Linux | [`symphony_linux_amd64.tar.gz`](https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/symphony_linux_amd64.tar.gz) | [`symphony_linux_arm64.tar.gz`](https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/symphony_linux_arm64.tar.gz) |

| Windows | [`symphony_windows_amd64.zip`](https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/symphony_windows_amd64.zip) | [`symphony_windows_arm64.zip`](https://github.com/feynmanzcys-bytes/symphony/releases/latest/download/symphony_windows_arm64.zip) |

В каждом архиве лежат программа (`symphony`, в Windows — `symphony.exe`), `LICENSE` и `README.md`. В `checksums.txt` релиза есть SHA-256 каждого архива.

#### Шаг 3: добавьте её в PATH

Установите программу из шага 2, `$d/symphony` (если ваша оболочка не сохраняет переменные между командами, впишите папку, которую вывел шаг 2). Возьмите папку, которая уже есть в `PATH` пользователя и доступна для записи без `sudo`: `~/.local/bin`, `/usr/local/bin` или `/opt/homebrew/bin`, именно в таком порядке.

```bash
install -m 755 "$d/symphony" ~/.local/bin/symphony
xattr -d com.apple.quarantine ~/.local/bin/symphony 2>/dev/null || true   # macOS: исполняемый файл не подписан
symphony -version          # выводит "symphony v1.4.0 (linux/amd64)": версию и платформу
```

Если ни одной из этих папок нет в `PATH`, спросите пользователя, прежде чем что-либо менять. Если он согласен, создайте `~/.local/bin`, добавьте её в rc-файл оболочки (`~/.zshrc` или `~/.bashrc`) и упомяните это в отчёте; если нет, установите программу туда, куда он скажет, и предупредите его, что mod не сможет сам запускать bridge, пока `symphony` нет в `PATH` его сеансов Claude Code (запуск при входе в систему из шага 5 всё равно работает).

В Windows распакуйте её в отдельную папку (`$d` и `$zip` — из шага 2; в новой оболочке задайте их снова):

```powershell
$dest = Join-Path $env:LOCALAPPDATA 'Programs\symphony'
Expand-Archive -LiteralPath (Join-Path $d $zip) -DestinationPath $dest -Force
& (Join-Path $dest 'symphony.exe') -version   # выводит "symphony v1.4.0 (windows/amd64)"
```

Добавить эту папку в `Path` пользователя — изменение надолго: сначала спросите пользователя. Если он согласен, выполните строку ниже и откройте новую оболочку; если нет, используйте полный путь. Распакованная через `Expand-Archive` программа не несёт отметки о загрузке, и SmartScreen её не останавливает; копию, распакованную через «Извлечь все» в Проводнике, он может остановить при двойном щелчке: нажмите «Подробнее», затем «Выполнить в любом случае».

```powershell
[Environment]::SetEnvironmentVariable('Path', [Environment]::GetEnvironmentVariable('Path', 'User') + ";$dest", 'User')
```

Если ваша собственная оболочка после этого не находит `symphony` (её `PATH` был прочитан до изменения), в остальных шагах указывайте абсолютный путь.

#### Шаг 4: установите mod

```bash
claude plugin install symphony-bridge --marketplace feynmanzcys-bytes/symphony
```

Эта команда добавляет репозиторий как маркетплейс плагинов `symphony` и устанавливает mod на уровне пользователя, без вопросов. Маркетплейсом может быть и локальный клон репозитория: `claude plugin install symphony-bridge --marketplace /absolute/path/to/symphony`. Тогда сеансы читают mod из этой папки, а `git pull` в ней его обновляет, поэтому держите такой клон в постоянном месте, а не во временной папке.

Проверьте:

```bash
claude plugin list --json   # у одной из записей "id": "symphony-bridge@symphony", "scope": "user", "enabled": true
```

- `"scope": "project"` или `"local"`: mod будет загружаться только в одной папке. Выполните `claude plugin uninstall symphony-bridge@symphony`, затем установите заново с `--scope user`.
- `"enabled": false`: выполните `claude plugin enable symphony-bridge@symphony`.

#### Шаг 5: запустите bridge

Если на шаге 1 нашёлся работающий bridge, сначала остановите его, как в разделе «Обновление» ниже: он работает на старой программе, а новая лишь найдёт его на этом адресе и уступит ему. Остановка bridge завершает запущенные им сеансы, поэтому заранее предупредите пользователя.

Спросите пользователя, должен ли symphony запускаться при каждом входе в систему.

Если да:

```bash
symphony -autostart on -open=false
```

Эта команда запускает bridge сейчас и при каждом входе в систему (пользовательская служба systemd в Linux, агент launchd в macOS, раздел реестра Run в Windows) и выводит после даты и времени:

```
symphony now starts when you log in (<where>); it's running at http://127.0.0.1:7788/?key=<key>
```

Если нет:

```bash
symphony -background -open=false
```

Эта команда запускает bridge отдельно от терминала (после перезагрузки компьютера он сам не запустится) и выводит в стандартный поток ошибок, после даты и времени:

```
the symphony bridge runs in the background at http://127.0.0.1:7788/?key=<key>; its log: <data folder>/bridge.log
```

Если bridge этой версии уже работает, вместо этого выводится (тем же образом) `a symphony bridge is already running at http://127.0.0.1:7788/?key=<key>`; это нормально, второй не запускайте. `<key>` — это ключ страниц, с которым браузер входит в офис: больше никуда его не вставляйте. Если программа отвечает `127.0.0.1:7788 is taken: another program, or a symphony bridge with another data folder, answers there`, скажите пользователю, что там отвечает (более старый bridge symphony тоже считается: остановите его, как в разделе «Обновление»), и не выбирайте другой адрес, не спросив его.

Проверьте всю цепочку одним запросом, который предъявляет ключ страниц из папки данных (через стандартный ввод, чтобы ключа не было в командной строке, которую могут увидеть другие пользователи):

```bash
printf 'X-Symphony-Key: %s\n' "$(cat "${SYMPHONY_DATA:-${XDG_CONFIG_HOME:-$HOME/.config}/symphony}/key")" | curl -s -H @- http://127.0.0.1:7788/api/launch/options      # Linux
printf 'X-Symphony-Key: %s\n' "$(cat "${SYMPHONY_DATA:-$HOME/Library/Application Support/symphony}/key")" | curl -s -H @- http://127.0.0.1:7788/api/launch/options   # macOS
```

```powershell
$data = if ($env:SYMPHONY_DATA) { $env:SYMPHONY_DATA } else { Join-Path $env:APPDATA 'symphony' }
(Invoke-WebRequest -UseBasicParsing -Headers @{ 'X-Symphony-Key' = (Get-Content (Join-Path $data 'key')) } -Uri http://127.0.0.1:7788/api/launch/options).Content
```

Папка данных — это `~/.config/symphony` в Linux (`$XDG_CONFIG_HOME/symphony`, если эта переменная задана), `~/Library/Application Support/symphony` в macOS и `%AppData%\symphony` в Windows, либо `SYMPHONY_DATA`, если она задана.

В ответе есть `"enabled":true` и `"mod":{"ok":true,"id":"symphony-bridge@symphony","version":"1.1.1"}`: bridge работает, нашёл `claude`, а mod установлен там, откуда его загрузят сеансы. При `"enabled":false` поле `mod.code` говорит, что не так, а `mod.fix` — команду, которая это исправит: `mod_not_installed` или `mod_project_scope` (вернитесь к шагу 4), `mod_disabled` (включите его), `mod_check_failed` (`claude plugin list --json` завершилась с ошибкой, так что Claude Code, скорее всего, слишком старый). `"mod":null` означает, что bridge вообще не нашёл `claude` в своём `PATH` (об этом написано в его журнале): добавьте его туда или запустите bridge с `-claude /path/to/claude`. Ответ с `"code":"page_key"` означает, что запрос не предъявил ключ или предъявил не тот: проверьте, что `cat` нашёл файл ключа (о папке данных — выше); если нашёл, то работающий bridge запущен с другой папкой данных.

Журнал bridge — это `bridge.log` в папке данных; если bridge запущен при входе в систему, журнал пишется в `journalctl --user -u symphony` в Linux и в `~/Library/Logs/symphony.log` в macOS.

#### Шаг 6: отчитайтесь пользователю

Откройте офис, запустив `symphony`: если bridge работает, она откроет офис в браузере по умолчанию, где вход уже выполнен, и завершится. Она также выводит адрес с `?key=`, по которому входит любой браузер на этом компьютере.

Сообщите пользователю:

- Чтобы открыть офис, запустите `symphony` (или дважды щёлкните по ней); просто `http://127.0.0.1:7788/` работает в браузере, где вход уже выполнен. Чтобы нанять первого сотрудника, нажмите «+» на свободном месте и выберите папку (или оставьте её пустой — будет новая собственная папка): там запустится сеанс Claude Code, внутри bridge, а его окно на странице — это его чат.
- Новые сотрудники следуют настройкам Claude Code пользователя (модель, глубина размышлений, режим разрешений), если в диалоге не выбрать другие. `bypassPermissions` выполняет любые команды и правки без вопросов, и тогда то, что читает сеанс, может заставить его выполнять команды от имени пользователя; когда этот режим выбран, диалог предупреждает об этом.
- Каждый сеанс расходует план Claude или кредиты API пользователя, как любой сеанс Claude Code; задача запускает от 2 до 5 сеансов одновременно.
- В офисе появляются только сеансы, запущенные со страницы (или вручную с `SYMPHONY_TOKEN`, см. «Запуск сеансов» ниже). Другие сеансы Claude Code пользователя, включая тот, что выполняет эту установку, там не видны.
- Что и куда установлено: путь к программе, mod на уровне пользователя, запускается ли bridge при входе в систему или работает в фоне, все изменения `PATH` или rc-файла, принятые вами решения и то, что `git` нет, если его нет.
- Как всё это отменить: см. «Удаление» ниже.

Правила: bridge принимает подключения только на этом компьютере (любой адрес не на этом компьютере он отклоняет; оставьте адрес по умолчанию `127.0.0.1:7788`, если только пользователь не выберет другой порт), не запускайте его через `sudo` и не запускайте второй bridge на том же адресе или с той же папкой данных (symphony откажется и назовёт уже работающий).

#### Обновление

Скачайте новый релиз, как в шаге 2. Работающий bridge использует старую программу, пока не перезапустится (а в Windows работающую программу нельзя заменить), поэтому остановите его командой `symphony -stop`, замените программу, как в шаге 3, и запустите его снова так же, как он работал раньше: `symphony -autostart on -open=false`, если он запускается при входе в систему (эта команда запускает его и сейчас), иначе `symphony -background -open=false`. Если bridge работает с `-addr` или `-data`, отличными от значений по умолчанию, передайте те же значения каждой из этих команд: `-stop` останавливает только bridge этой папки данных (на `-addr` или там, где bridge этой папки на самом деле работает) и выводит `nothing to stop`, если никто не отвечает. Остановка bridge завершает запущенные им сеансы, поэтому заранее предупредите пользователя. (`-stop` появился в v1.1.0; чтобы остановить bridge v1.0.0, завершите его процесс: `pkill -x symphony` в Linux и macOS, `Stop-Process -Name symphony` в Windows.)

Если программа установлена через Homebrew или Scoop, вместо скачивания и шага 3 выполните `brew update && brew upgrade symphony` (или `scoop update; scoop update symphony`), между тем же `-stop` и новым запуском. Если symphony запускается при входе в систему, запись автозапуска указывает на ссылку Homebrew на программу (`bin/symphony`), которую обновление переводит на новую версию; так что `-autostart on` здесь лишь запускает её снова сейчас.

Mod обновляется следом командой `claude plugin update symphony-bridge@symphony` (если маркетплейс — это клон, то вместо этого `git pull` в нём).

У программы и mod один номер версии; что изменилось в каждом релизе, описано в [CHANGELOG.md](CHANGELOG.md).

#### Удаление

```bash
symphony -stop                                    # останавливает bridge и его сеансы, как бы он ни был запущен (добавьте его -addr и -data, если они не по умолчанию)
symphony -autostart off                           # больше не запускает bridge при входе (а если автозапуск не был включён, так и сообщает)
claude plugin uninstall symphony-bridge@symphony  # mod
claude plugin marketplace remove symphony         # запись маркетплейса
rm ~/.local/bin/symphony                          # программа, куда бы её ни положил шаг 3
```

Если шаг 3 добавил `~/.local/bin` в rc-файл оболочки, удалите и эту строку. В Windows, в PowerShell:

```powershell
symphony -stop                                               # останавливает bridge и его сеансы (добавьте его -addr и -data, если они не по умолчанию)
symphony -autostart off                                      # больше не запускает bridge при входе
claude plugin uninstall symphony-bridge@symphony
claude plugin marketplace remove symphony
$dest = Join-Path $env:LOCALAPPDATA 'Programs\symphony'
Remove-Item -Recurse -Force $dest                            # программа
$p = ([Environment]::GetEnvironmentVariable('Path', 'User') -split ';' | Where-Object { $_ -and $_ -ne $dest }) -join ';'
[Environment]::SetEnvironmentVariable('Path', $p, 'User')    # запись в Path, которую добавил шаг 3
```

Если программа установлена через Homebrew, вместо строки с `rm` выполните `brew uninstall symphony` и `brew untap feynmanzcys-bytes/symphony`; если через Scoop — вместо последних четырёх строк PowerShell выполните `scoop uninstall symphony` и `scoop bucket rm symphony`.

Папка данных (учётные записи с их token, ключ страниц, журнал сообщений, учёт расходов, задачи, а также файлы вроде `lock`, `bridge.addr` или отложенного в сторону `*.corrupt-<time>`) остаётся; чтобы убрать всё, удалите и её. Собственные папки сотрудников (`symphony-bots` в домашней папке или папка, заданная в настройках) тоже остаются вместе с их работой. Вместе с ней удаляется и ключ страниц: при следующем запуске будет создан новый, и всем браузерам придётся войти заново. В Linux с браузером из snap или flatpak файл `open.html` лежит в собственной папке этого браузера (`~/snap/<snap>/common` или `~/.var/app/<app id>`); удалите и его.

## Что умеет

- **Каждый сеанс как чат**: нажмите на сотрудника, и его окно откроется посреди страницы: сверху кто он, ниже сеанс в виде чата: запросы, размышления модели (свёрнуты, оранжевое «Думает…», пока идут), её ответы по мере поступления, вызовы инструментов и сообщения от других сеансов фиолетовым. Напишите внизу, и текст дойдёт до сеанса как ваш запрос; кнопка «Остановить» прерывает его. То, что пишет модель, показывается как Markdown (заголовки, списки, таблицы, код, ссылки). Между двумя частями ответа её размышления и вызовы инструментов сворачиваются в одну строку: «Думает… 2 мин 38 с», пока она работает, и «Думал 2 мин 38 с», когда закончила; щелчок разворачивает шаги.
- **Подтверждения в браузере**: запросы разрешений (запуск команд, правка файлов) и вопросы AskUserQuestion поднимаются карточками поверх поля ввода в окне этого сотрудника (в теме «Коллеги» они стоят в разговоре там, где появились, и печатать при этом можно), а красный счётчик в верхней панели ведёт к ним. «Разрешить в этом сеансе» на карточке запроса разрешения пропускает такие же вызовы без вопросов до конца сеанса: любые правки, команду — по тому, как она начинается (`npm test`), или инструмент. Форма MCP-сервера тоже появляется карточкой; ответить на неё нужно в терминале сеанса, который карточка открывает прямо в окне. Если bridge не запущен, не знает учётную запись или ему нельзя доверять, сеанс, как обычно, спрашивает в терминале и никогда не зависает.
- **Пиксельный офис**: каждый сеанс — это сотрудник со своим постоянным местом. Зелёный — без дела, жёлтый — работает, красный — ждёт вашего разрешения или ответа, серый — не на работе. Сотрудники без дела сначала сидят на месте в телефоне или играют, потом идут гулять по офису: смотрят телевизор на диване в зоне отдыха, играют в настольный футбол и в догонялки, болтают за круглым столом, наливают кофе, смотрят в окно; со временем уходят вздремнуть, чаще всего прячутся в переговорной. Размер персонажа зависит от модели, а мускулатура — от глубины размышлений. Офис — это один этаж здания большой компании, и он заполняет всё окно: рабочий зал в центре, слева небольшие переговорные на 3–5 человек с табличками, справа переговорная и зона отдыха, а приходят и уходят на лифтах. В настройках можно выбрать и размер пикселей, из четырёх: тот же офис, с каждым шагом нарисованный более мелкими пикселями и подробнее.
- **Найти и позвать обратно**: щёлкните по сотруднику без дела — он вернётся на своё место и останется там до своего следующего хода; поле поиска в панели сверху находит сотрудников по имени, имени сеанса или папке (клавиша `/` переводит в него), а щелчок по счётчику рядом с ним (без дела, работают, ожидают, не на работе) выделяет всех сотрудников в этом состоянии. Язычок под панелью убирает её вверх и возвращает обратно.
- **Сообщения между сеансами**: когда сеансы пишут друг другу (SendMessage), через офис пролетает конверт, а сами сообщения сохраняются в журнале сообщений.
- **Запуск сеансов со страницы, без всплывающих окон**: нажмите «+» на свободном месте, чтобы нанять нового сотрудника, и выберите папку или оставьте её пустой: тогда сотрудник получит новую собственную папку в папке по умолчанию (`symphony-bots` в домашней папке; меняется в «Настройки → Сотрудники»), сразу с git-репозиторием, и в следующий раз вернётся туда же. Модель, глубина размышлений и режим разрешений следуют вашим настройкам Claude Code («По умолчанию»), если не выбрать другие; при выборе `bypassPermissions` появляется красное предупреждение о том, что он разрешает. Отметьте «Сказать ему, кто ещё в офисе» — и в системном промпте сеанса один раз за разговор будут названы остальные сеансы в сети, чтобы он мог писать им через SendMessage. Нажмите «За работу» в окне сотрудника, который не на работе, — и он вернётся на своё место с теми настройками, с которыми работал в последний раз. Сеанс работает в собственном терминале внутри bridge, так что ни одно окно не открывается и ничто не забирает фокус; «Открыть терминал» в окне сотрудника показывает этот терминал, когда нужно, а его закрытие ничего не меняет.
- **Команды в переговорных**: нажмите на свободную небольшую переговорную, напишите задачу и выберите от 2 до 5 участников: сотрудников (каждый получает второй сеанс только для этой задачи) или разовых консультантов. По умолчанию первый участник руководит и раздаёт части через SendMessage; каждый участник работает в своём git worktree, в своей ветке, так что никто не лезет в чужие файлы. Пока задача не закончится, участники сидят в переговорной.
- **Настройки и сообщение о проблеме**: кнопка «Настройки» (шестерёнка в теме «Коллеги») собирает то, что меняют изредка: язык, тему, светлую или тёмную, размер пикселей, остановку движения, шаги в развёрнутом виде. Всё, что пошло не так (сорвавшийся запуск или задача, ошибка API сессии, ошибка на странице), само записывается в журнал ошибок; чтобы сообщить о проблеме, нажмите там «Хочу сообщить о проблеме» и отправьте нам полученный файл по почте или приложите к issue на GitHub. В файле ошибки, версии и последние строки журнала bridge, но нет ключа, токенов и переписки.
- **10 языков**: English, 简体中文, 繁體中文, 日本語, 한국어, Español, Français, Deutsch, Português (Brasil) и Русский. Страница берёт язык браузера, а в настройках есть переключатель языка; сообщения bridge следуют `-lang`, иначе языку системы (`LANG` и подобным), иначе выводятся на английском; сообщения mod следуют `SYMPHONY_LANG` (у сеанса, запущенного со страницы, это язык страницы), иначе языку системы, иначе выводятся на английском.
- **Всё локально**: bridge — это одна программа на Go (только стандартная библиотека; сквозные тесты используют ещё chromedp), которая принимает подключения только на этом компьютере, страницы написаны на чистом JavaScript, и ничего не зависит от сторонних сервисов.

## Требования

- Claude Code 2.1.316 (проверено на этой версии). Для mod нужны function hooks из Claude Code, а это API пока в раннем доступе, поэтому после обновления Claude Code прогоните сквозные тесты.
- Для Linux, macOS и Windows есть готовая программа bridge; Go 1.27 или новее нужен только для сборки из исходников.
- `git` — только для совместных задач: каждый участник задачи работает в git worktree.
- Больше ничего: сеансы, запущенные со страницы, работают внутри bridge на любой платформе.

## Запуск bridge

`symphony` запускает bridge и открывает офис в браузере, где вход уже выполнен (`-open=false` отключает это). Браузер получает ключ страниц bridge в виде cookie через `open.html` — файл в папке данных, который можете читать только вы, так что ключ никогда не появляется в командной строке; в Linux, если браузер установлен из snap или flatpak, этот файл кладётся в собственную папку браузера, потому что такие браузеры не могут читать папку данных. Если открыть <http://127.0.0.1:7788/> в браузере, где вход не выполнен, появится страница, которая объясняет, как войти: снова запустить `symphony` или открыть адрес с `?key=`, который bridge вывел в свой журнал. <http://127.0.0.1:7788/approve> — упрощённая страница только для подтверждений. Если запустить `symphony` повторно, пока bridge работает, просто откроется офис. В Windows `symphony.exe`, запущенный двойным щелчком, работает в отдельном окне, а если закрыть это окно, bridge остановится.

| Флаг | По умолчанию | Что делает |
| --- | --- | --- |
| `-addr` | `127.0.0.1:7788` | Адрес, на котором принимать подключения. Хост должен быть `127.0.0.1`, `localhost` или `::1` (как в `[::1]:7788`); любой другой bridge отклоняет |
| `-data` | `$SYMPHONY_DATA`, иначе `symphony` в папке настроек | Папка данных: учётные записи с их token (`accounts.json`), ключ страниц (`key`) и `open.html`, журнал сообщений (`messages.json`), учёт расходов (`ledger.json`), задачи (`tasks.json`), настройки bridge (`settings.json`), журнал ошибок (`errors.json`), журнал `-background` (`bridge.log`), `lock` и `bridge.addr` (какой bridge её использует и где), а также повреждённые журнал сообщений, учёт расходов или настройки, отложенные в сторону как `*.corrupt-<time>` |
| `-claude` | `claude` | Исполняемый файл claude |
| `-lang` | язык системы, иначе `en` | Язык сообщений bridge (значение по умолчанию задают `SYMPHONY_LANG`, `LC_ALL`, `LC_MESSAGES` или `LANG`) |
| `-mod` | пусто | Для разработки: передавать сеансам mod из этой папки через `--plugin-dir` вместо установленной копии |
| `-web` | пусто | Для разработки: отдавать страницы из этой папки, чтобы правки были видны после перезагрузки |
| `-open` | `true` | Открыть офис в браузере, когда bridge запустится; если на `-addr` уже работает bridge с этой папкой данных, просто открыть его офис |
| `-autostart` | — | `on`: запускать bridge при каждом входе в систему, с остальными указанными флагами, и запустить его сейчас; `off`: отменить это |
| `-background` | — | Запустить bridge в фоне, отдельно от терминала, с журналом в `bridge.log` в папке данных, и вернуться, когда он ответит |
| `-stop` | — | Остановить bridge этой папки данных (на `-addr`, а иначе там, где он работает), как бы он ни был запущен (его сеансы завершатся), и вернуться, когда он завершится; ключ страниц предъявляется только тому bridge, который докажет, что этот ключ у него есть |
| `-version` | — | Показать версию и выйти |

Если на `-addr` отвечает что-то другое (другая программа, bridge с другой папкой данных или более старый bridge symphony), symphony сообщает об этом и останавливается; ключ страниц она предъявляет только тому bridge, который докажет, что этот ключ у него есть. Папкой данных одновременно пользуется только один bridge: если symphony запущена с папкой данных, чей bridge уже работает на другом адресе, она сообщает, где он работает, открывает его офис и останавливается (второму bridge задайте собственную папку данных через `-data`).

**Запуск при входе в систему**: `symphony -autostart on` запускает bridge при каждом входе в систему, с переданными вместе флагами (например, `-addr`), и сразу же запускает его; `symphony -autostart off` отменяет это. В Linux это пользовательская служба systemd (журнал — `journalctl --user -u symphony`), в macOS — агент launchd (журнал в `~/Library/Logs/symphony.log`), в Windows — значение в разделе реестра Run (bridge работает в окне консоли; если его закрыть, bridge остановится до следующего входа). `symphony -stop` останавливает bridge, как бы он ни был запущен, до тех пор, пока его не запустят снова (а запущенный при входе в систему — до следующего входа). Нужна сама программа symphony, а не `go run`. Bridge, запущенный при входе в систему, не получает от вашей оболочки ничего, кроме `PATH`, поэтому `-autostart on` ещё и сохраняет переменные, которые могут понадобиться его сеансам, в том виде, в каком они заданы в вашей оболочке при запуске этой команды: `CLAUDE_CONFIG_DIR`, прокси (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY`, в верхнем или нижнем регистре), `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` и `SSL_CERT_DIR` — и больше ничего (никаких ключей API) — в файле `autostart-env.json` в папке данных, который можете читать только вы; изменив их, выполните команду снова. Bridge, который не может запуститься (его папкой данных пользуется другой bridge, повреждён `accounts.json`, на его адресе работает что-то другое), перезапускается несколько раз, а потом его оставляют в покое: в Linux — 5 попыток за минуту (почему — скажет `systemctl --user status symphony`), в macOS — одна попытка в минуту (почему — видно в журнале); устраните причину и снова выполните `symphony -autostart on` или просто войдите в систему заново.

**Из исходников**, с Go 1.27 или новее: `git clone https://github.com/feynmanzcys-bytes/symphony.git && cd symphony && go run ./cmd/bridge`.

## Запуск сеансов

**Со страницы**: нажмите «+» на свободном месте, введите имя и выберите папку и параметры. Bridge запускает `claude` в собственном терминале внутри себя: окно не открывается. Окно сотрудника показывает сеанс в виде чата, а его кнопка «Открыть терминал» открывает окно терминала, подключённое к сеансу (`symphony attach <id>` делает то же самое из любого терминала, с `-addr` и `-data`, если bridge использует не значения по умолчанию; если окно терминала открыть не удаётся, точную команду показывает страница. `Ctrl-]` или закрытие окна отключает, а сеанс продолжается). Сеансы — дочерние процессы bridge: остановка bridge завершает их. Когда сеанс завершается — его остановили со страницы, он остановился вместе с bridge или закончился сам, — вместе с ним завершается и то, что он оставил работать в фоне (например, команда, которую инструмент отправил в фон через `&`): в Windows всё это завершает объект задания (job object) сеанса; в Linux и macOS bridge находит эти процессы по id запуска в их окружении, но в macOS он не может прочитать окружение собственных программ Apple (`/bin/sleep`, `bash`, `zsh`, `perl`: система скрывает их окружение от `ps -E`), так что оставшийся после сеанса сервер `node` или из Homebrew завершится, а простой `sleep` или скрипт оболочки — нет.

**Из терминала**: создайте учётную запись, чтобы получить token, предъявив ключ страниц, и запустите `claude` с этим token:

```bash
printf 'X-Symphony-Key: %s\n' "$(cat ~/.config/symphony/key)" | curl -H @- -X POST 127.0.0.1:7788/api/accounts -d '{"name":"frontend-alice"}'   # в ответе будет token
SYMPHONY_TOKEN=<token> claude --name frontend-alice --permission-mode manual
```

Файл ключа — это `~/.config/symphony/key` в Linux, `~/Library/Application Support/symphony/key` в macOS и `%AppData%\symphony\key` в Windows, либо `key` в папке, которую указывает `-data` / `SYMPHONY_DATA`.

Рекомендуем режим разрешений `manual`: в режиме `auto` большинство действий выполняется без вопросов, так что до страницы доходит мало запросов. Если bridge работает не на адресе по умолчанию, задайте ещё `SYMPHONY_BRIDGE`: `http://127.0.0.1:<port>`, `http://localhost:<port>` или `http://[::1]:<port>` на этом компьютере либо адрес `https://`; с любым другим значением mod никогда не обращается к bridge. `SYMPHONY_LANG` задаёт язык сообщений mod (иначе язык системы, иначе английский).

Прежде чем сеанс куда-либо отправит свой token, mod проверяет, что bridge по этому адресу знает этот token, не отправляя его (`POST /api/hello`). Если bridge не может принять сеанс, сеанс показывает одно из этих сообщений, его подтверждения остаются в терминале, и он никогда не зависает:

| Сообщение | Что это значит |
| --- | --- |
| `не удаётся подключиться к bridge` / `can't reach the bridge` | По адресу bridge никто не отвечает, и запуск bridge не помог (или адрес не на этом компьютере). |
| `не удалось запустить bridge (...): <reason>` / `couldn't start the bridge ...: <reason>` | Никто не ответил, и команда `symphony -background` не сработала по указанной причине (например, bridge этой папки данных работает на другом адресе: укажите этот адрес в `SYMPHONY_BRIDGE`). |
| `bridge не знает этот SYMPHONY_TOKEN` / `the bridge doesn't know this SYMPHONY_TOKEN` | У bridge нет учётной записи с этим token: её удалили, или bridge использует другую папку данных. |
| `отвечает не bridge symphony, которому этот сеанс может доверять` / `isn't a symphony bridge this session can trust` | По адресу что-то отвечает, но не может доказать, что знает token: другая программа или symphony старше mod (обновите его). Token не отправляется. |
| `SYMPHONY_BRIDGE (...) должен быть на этом компьютере или использовать https` / `SYMPHONY_BRIDGE ... must be on this machine or use https` | Адрес не из тех, что принимает mod; к bridge он не обращается вовсе. |
| `у этой учётной записи уже есть сеанс онлайн` / `this account already has a session online` | Одна учётная запись обслуживает один сеанс за раз; создайте для этого сеанса другую учётную запись. |
| `ждём вашего ответа на странице офиса` / `waiting for your answer in the office page` | Запрос разрешения или вопрос ждёт на странице офиса, а не в терминале; ответьте там или нажмите Esc, чтобы отменить его. Показывается один раз за сеанс. |

Если по адресу bridge на этой машине никто не отвечает, сеанс сам запускает bridge командой `symphony -background -open=false -addr <that address>` (если `symphony` есть в вашем PATH) и сообщает об этом (`bridge (...) запущен в фоне` / `started the bridge ... in the background`); bridge продолжает работать после завершения сеанса. Задайте `SYMPHONY_DATA`, если ваши учётные записи лежат не в папке данных по умолчанию. Если bridge этой папки данных уже работает на другом адресе, сеанс сообщает об этом и спрашивает в терминале: укажите этот адрес в `SYMPHONY_BRIDGE`.

## Совместные задачи

В небольшой переговорной команда из 2–5 сеансов вместе работает над одной задачей. Для задач нужен `git`.

**Как начать задачу**: нажмите на свободную небольшую переговорную и опишите, что нужно сделать. Отметьте участников в нужном порядке (от 2 до числа мест в переговорной), выберите каждому модель и глубину размышлений, а всей команде — режим разрешений (по умолчанию — собственные настройки Claude Code; сотрудник, который уже работал, начинает с последних модели и глубины размышлений; при выборе `bypassPermissions` появляется предупреждение), и нажмите «Начать задачу». Участники бывают двух видов:

- **Сотрудник**: получает второй сеанс только для задачи, и этот сеанс работает в папке сотрудника; его собственный сеанс на рабочем месте остаётся как был. Сотрудник участвует только в одной задаче за раз, а у того, кто ещё ни разу не работал, пока нет папки: сначала один раз нажмите для него «За работу».
- **Консультант**: разовый участник, созданный для задачи с обычными полями (имя, папка, модель, глубина размышлений). У него нет рабочего места, он приезжает на лифте и исчезает, когда задача заканчивается.

**Лидер**: по умолчанию первый участник руководит: делит задачу, раздаёт части через SendMessage, проверяет работу, сливает ветки остальных в свою и рассказывает вам, что сделано. Снимите отметку лидера — и каждый получит всю задачу, а распределят её участники между собой. В обоих случаях bridge отправляет каждому участнику первый запрос: кто в команде (участники находят друг друга по имени через SendMessage), ветки каждого и правила.

**Git**: каждый участник работает в своём git worktree, в своей ветке своей папки, `symphony/<task id>/<member>` (например, `symphony/T1/bob`; второй участник с тем же именем получает `-2`), так что никто не лезет в чужие файлы, а ваша собственная рабочая копия остаётся как была. Worktree лежат внутри папки, в `.symphony/worktrees/`, и git их не видит благодаря `.git/info/exclude` (ваш `.gitignore` не трогается). Когда задача заканчивается, всё, что участник не закоммитил, коммитится в его ветку, файлы, которые git игнорирует в его worktree (результаты сборки, `.env`, `node_modules` и тому подобное), переносятся в папке в `.symphony/kept/<member>-<task id>/`, а worktree удаляются. symphony никогда не удаляет `.symphony/kept/`; удалите её сами, когда её содержимое станет не нужно.

- В ваших собственных репозиториях ничего не сливается: ветки остаются, и сливаете их вы; если есть лидер, в его ветке собрана работа всех.
- Папка, которая не является git-репозиторием, становится им для задачи и остаётся им: `git init`, затем коммит всего, что в ней лежит, кроме файлов, в которых часто бывают секреты или которые много весят (`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ecdsa*`, `id_ed25519*`, `.npmrc`, `.netrc`, `.pypirc`, `node_modules/`, `.DS_Store`); их список записывается в `.git/info/exclude`. Эти файлы остаются в папке, но в worktree участников их нет, так что участник, которому они нужны, устанавливает или создаёт свои. Когда задача заканчивается, ветки участников сливаются в ветку папки, так что в папке оказывается результат; `.git` и ветки сохраняются. Если задачу не удалось начать, папка снова становится обычной.
- Если слияние не удалось, оно отменяется и базовая ветка остаётся такой, как была; ветки остаются вместе с работой на них, а окно задачи показывает, в какой ветке конфликт. Если при завершении задачи не удалось что-то ещё, это остаётся как есть, а окно задачи показывает, что именно не удалось.

**В офисе**: всю задачу участники сидят за столом в переговорной, а на месте сотрудника тем временем стоит пустой стул. На табличке переговорной виден номер задачи; её огонёк, зелёный, пока переговорная свободна, становится жёлтым, пока идёт задача, и красным, пока кто-то из участников ждёт вашего разрешения или ответа. Нажмите на переговорную, чтобы открыть окно задачи: сама задача, участники с их папками и ветками, чат команды и «Завершить задачу». Щелчок по фигурке участника в переговорной тоже открывает окно задачи; щелчок по участнику в окне задачи открывает его окно чата рядом — такое же, как окно сотрудника, и только для одного участника за раз (щёлкните по другому участнику, чтобы переключиться). Красный счётчик в верхней панели и поле поиска открывают участника задачи так же.

**Чат команды**: в окне задачи видны сообщения, которые участники отправляют друг другу, — у каждого пиксельная фигурка и имя отправителя, а текст начинается с `@` и адресата. Ниже есть поле, чтобы вы сами писали команде: `@bob-T1 …` уйдёт только этому участнику (несколько `@names` — всем им; если набрать `@`, откроется список участников, выбрать можно стрелками, Enter или щелчком), а сообщение без `@` уйдёт всем в задаче. Enter — отправить, Shift+Enter — новая строка.

Задача заканчивается, когда вы завершаете её в окне задачи или когда заканчивается её последний сеанс: bridge останавливает сеансы участников, разбирается с git, как описано выше, и удаляет консультантов. Задача, которая ещё шла, когда bridge остановился, завершается так же при следующем запуске bridge.

## Учётные записи и места

- Учётная запись в symphony — это имя, token и постоянное место. Одна учётная запись обслуживает один сеанс за раз и ещё один в задаче, в которой участвует; любой другой сеанс получит отказ, и его подтверждения останутся в терминале.
- Вход в Claude здесь не настраивается: все сеансы могут работать под одним логином Claude.
- Данные хранятся в `~/.config/symphony` (Linux), `~/Library/Application Support/symphony` (macOS) или `%AppData%\symphony` (Windows), либо там, куда указывает `-data` / `SYMPHONY_DATA`. В `accounts.json` лежат token, а в `key` — ключ страниц; читать оба файла может только владелец (0600); в Windows их защищают права доступа к папке пользователя.

## Расходы и разрешения

- Каждый сеанс, который запускает symphony, — это сеанс Claude Code, и он расходует ваш план Claude или кредиты API, как любой другой. Opus с максимальной глубиной размышлений расходует их быстро, а задача запускает от 2 до 5 сеансов одновременно.
- `bypassPermissions` выполняет любые команды и правки без вопросов. Тогда то, что читает сеанс (файл, веб-страница, вывод инструмента), может заставить его выполнять команды от вашего имени. Диалоги запуска и задачи показывают красное предупреждение, когда вы его выбираете; по умолчанию они следуют вашим настройкам Claude Code.
- Для сеансов, запущенных со страницы, bridge сам отвечает на вопрос Claude Code о доверии к папке («trust this folder»), поэтому запускайте сеансы только в папках, которым доверяете.
- «Разрешить в этом сеансе» действует до конца сеанса и пропускает только то, о чём Claude Code спросил бы, в пределах ваших настроек разрешений: никогда — команду, соединённую с другой (`;`, `&&`, `|`, перенаправление), и никогда — в обход запрещающего правила (deny) или настроек вашей организации. Правило для команды покрывает все команды, которые начинаются так же (`npm test` покрывает и `npm test -- --watch`).

## Безопасность

Страница умеет запускать сеансы, а значит, выполнять команды на этом компьютере, поэтому bridge следит за тем, кто к нему обращается:

- **Ключ страниц**: офису и его API нужен ключ страниц — cookie, которую браузер получает по ссылке, открываемой `symphony`. Ключ — это файл `key` в папке данных, читать который можете только вы; программы передают его в заголовке `X-Symphony-Key`.
- **Только этот компьютер**: bridge слушает и принимает подключения только на этом компьютере. Он отклоняет запросы, адресованные любому другому хосту (DNS rebinding), и запросы на запись, которые другие сайты отправляют через ваш браузер, а его API не отвечает ни на один запрос, который, по словам вашего браузера, пришёл с другого сайта или другого порта, даже на переход по ссылке. Другие сайты не могут встроить его страницы во фрейм. Страницы загружают только собственные файлы bridge (Content Security Policy).
- **Mod проверяет bridge**, прежде чем отправить свой token, а программа `symphony` — прежде чем предъявить ключ страниц, так что ни то, ни другое не достанется чему-то другому, что слушает по адресу bridge.
- **От чего это не защищает**: программы, работающие от имени вашего пользователя, могут прочитать ключ страниц и token в папке данных, как и любые ваши файлы. Кроме того, браузеры отправляют cookie сайта на любой его порт: сервер, который другой пользователь этого компьютера запустил на `127.0.0.1`, получит cookie ключа страниц, когда ваш браузер его откроет или когда этот сервер займёт порт bridge, пока bridge остановлен, а офис ещё открыт во вкладке. На компьютере, которым пользуетесь не только вы, закрывайте офис, прежде чем остановить bridge, а если ключ мог утечь, удалите файл `key` в папке данных (при следующем запуске будет создан новый).
- Программы не подписаны. macOS может отказаться открывать копию, скачанную через браузер, потому что не может проверить разработчика: нажмите «Все равно открыть» в разделе «Системные настройки» → «Конфиденциальность и безопасность» или один раз выполните `xattr -d com.apple.quarantine symphony`. В Windows SmartScreen может остановить при двойном щелчке копию, распакованную через «Извлечь все» в Проводнике: нажмите «Подробнее», а затем «Выполнить в любом случае» (`Expand-Archive`, которым пользуется установка, не оставляет на ней отметки о загрузке). В `checksums.txt` релиза есть SHA-256 каждого архива, а каждый архив снабжён аттестацией GitHub о том, где он собран; шаг 2 установки проверяет и то и другое.

Как сообщить об уязвимости, описано в [SECURITY.md](SECURITY.md).

## Разработка

```bash
go test -race ./...                         # модульные тесты bridge и переводов
claude plugin test mods/symphony-bridge     # модульные тесты mod
claude plugin validate .                    # проверка маркетплейса
claude plugin validate mods/symphony-bridge  # проверка mod
SYMPHONY_E2E=1 go test -tags e2e -v -count=1 -timeout 20m ./e2e/   # сквозные тесты: запускают настоящие сеансы и тратят токены
```

- Участие в разработке: в [CONTRIBUTING.md](CONTRIBUTING.md) описаны подготовка окружения, проверки перед pull request и правила; [CLAUDE.md](CLAUDE.md) — подробная карта кода.
- Работа над mod: `go run ./cmd/bridge -mod mods/symphony-bridge` — и сеансы, запущенные со страницы, получат вашу копию mod через `--plugin-dir`; в сеансы, которые вы запускаете вручную, добавьте `--plugin-dir mods/symphony-bridge` сами.
- Работа над страницами: `go run ./cmd/bridge -web web` — и правки видны после перезагрузки.
- Чтобы посмотреть на офис без настоящих сеансов, запустите второй bridge с собственной папкой данных и наполните его выдуманной активностью: `D=$(mktemp -d)`, `go run ./cmd/bridge -addr 127.0.0.1:7799 -data "$D"`, затем в другом терминале (с тем же `D`) `go run ./cmd/demo -base http://127.0.0.1:7799 -data "$D"` (demo берёт ключ страниц bridge из этой папки данных).
- Скриншоты в этом README: `SYMPHONY_E2E=1 SYMPHONY_E2E_DOCS=1 go test -tags e2e -run TestDocsScreens ./e2e/` снимает их заново с выдуманной активностью (без токенов).
- Переводы: каждый язык — это один файл, `web/locales/<lang>.json` для страниц и `internal/i18n/locales/<lang>.json` для bridge, с теми же ключами, что и в `en.json`; немногие сообщения самого mod лежат в `mods/symphony-bridge/hooks/messages.ts`. Модульные тесты проверяют, что в каждом языке есть все ключи и те же `{placeholders}`, а сквозной тест `TestI18n` открывает страницы на каждом языке.
- Сквозным тестам нужны claude, tmux (для сеансов, которыми тесты управляют сами) и Chromium или Chrome, поэтому они запускаются на Linux и macOS. `TestOffice` и `TestModStartsBridge` запускают настоящие сеансы и тратят токены; остальные — нет. По умолчанию тесты берут mod из этого репозитория; чтобы использовать установленный mod, задайте `SYMPHONY_E2E_MOD=installed`. Скриншоты сохраняются в `e2e/artifacts/`.
- Релизы: поднимите версию в `mods/symphony-bridge/.claude-plugin/plugin.json`, добавьте в `CHANGELOG.md` раздел `## vX.Y.Z (date)`, перенесите dev в main, затем поставьте тег на этот коммит в main и отправьте тег (`git tag -a v1.0.0 -m v1.0.0 && git push origin v1.0.0`); GitHub Actions проверит, что тег совпадает с версией в `plugin.json` и что раздел есть, соберёт программу для всех платформ, заверит аттестацией, где собраны архивы, и опубликует релиз, заметки к которому начинаются с этого раздела (`.github/workflows/release.yml`; суффикс вроде `-rc.1` делает пре-релиз); для релиза, который не является пре-релизом, workflow затем сделает коммит formula для Homebrew и manifest для Scoop в main (и в dev, если это fast-forward), так что после этого сделайте pull обеих веток. `.github/release.sh v1.0.0 dist` собирает такие же архивы локально, а на Linux — байт в байт.
